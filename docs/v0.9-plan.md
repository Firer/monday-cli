### M51 — multi-level board awareness (pre-flight `4eb3ca4..2958146`, CONVERGED; IMPL `f63218d..4d39e4d`, CONVERGED 2026-05-22)

**Runtime read FIRST (R-v0.9-NEW-1).** The §1 M51 row's framing —
"M50 retains the `hierarchy_type` fetch on the parent lookup ... so M51
wires the same field into the board projection" — is **inaccurate**, and
reading the runtime corrected it before the contract was written:

- **`board describe` ALREADY emits `hierarchy_type`** (since v0.3 —
  `src/api/board-metadata.ts` selects it via raw GraphQL;
  `board/describe.ts` projects it through `boardMetadataSchema`). So
  the §1 row's "`board get`/`describe`/`list`" overstates: **describe
  needs no change.** The real gap is `board get` + `board list`.
- **M51 does NOT consume the item-parent-lookup fetch.** That fetch
  (`lookupItemBoardWithHierarchy` → `ITEM_PARENT_LOOKUP_QUERY`) lives on
  the `items(...) { board { hierarchy_type } }` path; M51's surfacing is
  a **separate** `boards(...)` query (board get/list) + the shared
  mutation-cluster fragment. The two never meet — see D8.

**The architecture wrinkle (drove D2).** `board get`'s output schema
*is* the shared `boardProjectionSchema` + `BOARD_FIELDS_FRAGMENT`
(`src/api/board-projection.ts`), also used by `board create` /
`update` / `archive` / `delete` / `duplicate` and `projectMutationBoard`.
The M15 design deliberately single-sources that shape ("a successful
create/update/duplicate returns the exact JSON shape a follow-up
`board get` would return"). So "add `hierarchy_type` to `board get`"
cannot be scoped to get alone without *breaking* that invariant.

- **D1 — Field shape.** `hierarchy_type: z.string().nullable()`
  (required key, nullable value) on `boardProjectionSchema` + the
  `board list` `boardSchema`. Mirrors `boardMetadataSchema.hierarchy_type`
  exactly (the describe path). NOT a closed enum — Monday returns
  internal forms (`classic`, `multi_level`, and legacy `top_level` /
  `parent` seen in fixtures), so a free-form string keeps the projection
  robust; the agent-facing values documented in cli-design §2.8 are
  `classic` | `multi_level`. Selected in the wire after `url` (mirrors
  `BOARD_METADATA_QUERY`'s position).
- **D2 — Scope: extend the shared projection** (USER DECISION
  2026-05-22, neutral-trade-offs question). `hierarchy_type` is added to
  `BOARD_FIELDS_FRAGMENT` + `boardProjectionSchema`, so it surfaces on
  `board get` AND the mutation cluster (`create` / `update` / `archive`
  / `delete` / `duplicate`); `board list` (its own inline query/schema)
  gains it separately. Preserves the M15 one-canonical-Board-shape
  invariant, and `board duplicate`'s result then confirms whether the
  copy preserved `multi_level` (ties to Half 2). The rejected
  alternative — decouple `board get` into its own query/schema (get +
  list only) — would have broken the M15 invariant for a *smaller* diff.
  **`board find` stays OUT** (its `BoardFind` doc is a narrow projection
  — selects `url` but omits `board_folder_id` / `items_count` /
  `updated_at` / `permissions` — by design; adding `hierarchy_type`
  there is a separate, unrequested widening).
  **`board describe` unchanged** (already emits it).
- **D3 — ERROR_CODES delta: ZERO** (stays 29). Additive read field; no
  new failure mode.
- **D4 — Command delta: ZERO** (stays 117). No new verb/flag; existing
  verbs gain an output field.
- **D5 — Required, not optional.** `boardProjectionSchema` parses live
  wire responses + hand-built dry-run snapshots — it is **never** used
  to parse on-disk cache (that's `boardMetadataSchema`, which made
  `is_leaf` / `items_count` optional for old-cache back-compat). The
  wire always returns `hierarchy_type` (real `Board` field, verified
  live at `2026-01` by the M50 probe), so required-nullable is correct
  and means a future Monday field-removal (the `is_leaf` scenario)
  surfaces as a hard parse error caught by the D7 smoke test rather than
  silently. Consequence: every hand-built `BoardProjection` (the
  archive + duplicate dry-run snapshots) and every projection-path test
  fixture/cassette must add the key.
- **D6 — Dry-run snapshots.** `board archive` + `board duplicate`
  dry-run snapshots gain `hierarchy_type: current.hierarchy_type`
  (sourced from `loadBoardMetadata`, which already fetches it). `board
  create` (argv-only) + `board delete` (minimal) dry-runs carry no board
  snapshot — unaffected. `board update` dry-run emits a field-diff, not
  a projection — unaffected.
- **D7 — RUN_LIVE_TESTS smoke test.** Extend the live schema-drift
  guard (`tests/e2e/live-schema-drift.test.ts`) to run the board
  get/list query (the shared fragment) against the live API so a future
  Monday removal of `hierarchy_type` surfaces under `RUN_LIVE_TESTS=1`
  — frozen fixtures alone masked the `is_leaf` live breakage (memory
  `project-is-leaf-live-drift`; testing.md "mock must reject what the
  wire rejects").
- **D8 — R-v0.9-NEW-4 (item-lookup fetch): KEEP, resolve at close.**
  M51 surfaces `hierarchy_type` via the separate `boards(...)` query, so
  the item-parent-lookup `hierarchy_type` (`lookupItemBoardWithHierarchy`)
  is genuinely read-but-unused after M51 (confirmed: `create.ts`'s
  `lookupParent` returns `{boardId, hierarchyType}` and the call site
  reads only `boardId`). **Decision: KEEP it.** Dropping it would force
  swapping `operation_name` `ItemParentLookup` → `ItemBoardLookup` across
  ~23 mock sites — including the freshly-shipped M50 regression tests
  that deliberately drive classic/multi_level parent fixtures to prove
  the unified dispatch ignores `hierarchy_type` — for the marginal
  benefit of one Board scalar. The retained `{boardId, hierarchyType}`
  return is a deliberate tripwire: a future dev re-adding a

- **D1 — Routes.** Two:
  - (a) `boardMetadataSchema` gains a `views: z.array(boardViewSchema)
    .nullable()` slot — **required key, nullable value** (`.nullable()`,
    NOT `.optional()`). Two reasons, both load-bearing:
      1. `Board.views` is nullable on the wire (introspected:
         `LIST<BoardView>`, not `NON_NULL<LIST>`), so a `views: null`
         live response must parse cleanly; the projection normalizes
         to `[]` via `?? []`.

         cache entries: a cache entry without the `views` key fails
         strict-parse, the `parseCacheEntry` ZodError is swallowed by
         `loadBoardMetadata`'s try/catch (the "corrupt cache → cache-

         call re-fetches live. So pre-M52 caches retire automatically

    describe`'s output gains a `views: BoardView[]` slot (projected

  const jsonScalarOrNull = z
