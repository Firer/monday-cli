### M50 — multi-level subitem nesting (pre-flight CLOSED 2026-05-22, `9675f6a..e41b467`)

**Probe basis:** the 2026-05-22 dev-board sweep (§2) IS the wire
probe — no new probe run. All facts verified at API `2026-01` (the
CLI's pin, NOT SDK-gated).

**Headline finding (drove the scope).** The current runtime gate is
*inverted*. `src/commands/item/create.ts` rejects ONLY
`hierarchy_type === 'multi_level'` — the case the probe proved WORKS
(depth-3+) — while classic / `top_level` / `null` boards already
create subitems (shipped M9, v0.2). The genuinely-unsupported case
(classic *deep* nesting, subitem-of-a-subitem) is what the M28 premise
was really about, and it is already handled accurately by
`deriveSubitemsBoardId` ("no subtasks column") when `--set` is present.
So M50 IMPL is a *deletion* of the false-claim gate, not a
re-implementation. `item subitems` already reads multi-level
hierarchies (hierarchy-agnostic `subitems` connection); no read-side
gap.

**Decision: MINIMAL LIFT** (user-confirmed 2026-05-22 — the unified
single-path option over an explicit classic-board guard).

- **D1 — Dispatch.** Delete the `hierarchy_type === 'multi_level'`
  rejection block (`create.ts:735-752`). Classic AND multi-level flow
  through ONE `create_subitem` + `deriveSubitemsBoardId` path; no
  `hierarchy_type` branch. The `subtasks` column's
  `settings_str.boardIds[0]` transparently yields the correct
  column-resolution target — a separate sub_items_board on classic
  boards, the self-referenced host board on multi-level boards
  (the column self-references via `settings_str.boardIds[0]` →
  `[<self>]`). Dry-run and live share `resolveCreateMode`, so both
  lift together.
- **D2 — Classic-board treatment.** The false-claim `multi_level`
  rejection is DELETED outright (no message relocation). NO
  `hierarchy_type`-keyed rejection survives, and NO `deferred_to` slot
  anywhere (keeping `deferred_to: 'v0.9'` while shipping AT v0.9 is the
  R-NEW-82 "wait for the version you're already running" anti-pattern).
  The only board-capability gate is the existing data-model
  `deriveSubitemsBoardId` `usage_error` ("no subtasks column / no
  settings / no linked board"), which fires when `--set` targets a
  board with no subitems lane — accurate, no false claim. Classic
  deep-nesting WITHOUT `--set` falls through to Monday's server-side
  response (the user accepted this over a friendly pre-mutation guard,
  which would have cost an extra parent-board lookup on every subitem
  create).
- **D3 — Dry-run envelope.** No shape change. The §6.4 "Subitem
  variant" (`operation: "create_subitem"`, `parent_item_id`,
  `board_id` omitted, same `resolved_ids` / `diff`) applies to
  multi-level boards identically; M50 only lifts the gate that
  currently blocks the dry-run from reaching it. cli-design §6.4
  "Classic boards only" qualifier corrected to "Both hierarchy types".
- **D4 — `item subitems` read parity.** Already holds — no change.
  `item subitems` reads Monday's hierarchy-agnostic
  `items(ids) { subitems { ... } }` connection, which returns direct
  children regardless of the classic/multi-level model. Deep reads
  compose via recursive `monday item subitems` calls (documented at
  the command; same on multi-level).
- **D5 — ERROR_CODES delta.** ZERO. Registry stays 29. M50 REMOVES a
  `usage_error` path (the multi_level rejection) and adds none; the
  surviving `deriveSubitemsBoardId` rejections are existing
  `usage_error`s. 117 commands unchanged (no new verb).

**Pre-flight stub: NOT APPLICABLE.** The R-NEW-76 parseArgv-before-
c8-ignore stub convention anchors NEW deferred wire legs; M50 adds
none — `create_subitem` is the existing M9 mutation, live for classic
