# v0.4 implementation plan

> **Status:** plan, not contract. The binding contract is
> [`cli-design.md`](./cli-design.md). This document sequences the
> work needed to ship v0.4 of that contract; it doesn't redefine it.
> If a conflict arises, `cli-design.md` wins and this plan is updated.

## 1. Scope summary

v0.4 is "**polish + nice-to-haves** — agents *react* and *attach*,
not just *narrate* and *write*." v0.3 closed the v0.1/v0.2 narration
gap (cross-board reads, item history, partial-success bulk) and the
v0.1/v0.2 outbound-write gap (notifications, webhooks). v0.4 picks
up the remaining cli-design §13 v0.4 candidates: a polling-based
reactivity primitive (`item watch`) so agents can wait for state
changes without scripting their own polling loop, bulk throughput
via `--concurrency` against Monday's per-account concurrency cap,
asset upload (`add_file_to_column` / `add_file_to_update`) so an
agent can attach evidence to its writes, read-only `doc list/get`,
`team` create/manage to close the noun gap, and shell completion
(bash / zsh / fish) for the rare human user. None of these are
load-bearing for the agent-narration story v0.3 already shipped —
v0.4 is what an agent reaches for when the v0.3 surface isn't
enough, not what the agent needs to do its day-one job.

**In scope (from `cli-design.md` §13 v0.4 + Appendix B verb-noun
matrix):**

| Group | Commands |
|-------|----------|
| **reactivity** | `item watch <iid>` (polling-based event stream over the M24 `item history` projection; emits NDJSON event records as state changes; see cli-design §14.4 for the cadence + circuit-breaker pre-flight question). |
| **bulk throughput** | `--concurrency <N>` extension to the v0.2 fail-fast bulk path + the v0.3-M25 partial-success bulk path. Probed against Monday's per-account concurrency cap (was surfaced as `concurrency_exceeded` in earlier API versions; verify still canonical at API `2026-01`). |

| **read-only docs** | `monday doc list` (account-scoped doc directory); `monday doc get <doc-id>` (doc body + metadata). Read-only; full docs CRUD deferred further per cli-design §13 v0.4 entry. |
| **team CRUD** | `monday team create` / `monday team update` / `monday team delete` (Appendix B already lists list/get/create/delete; v0.4 lands the writer surface). |

**Universal partial-success rule (cli-design §6.1 compliant — same
shape as v0.2/v0.3).** Multi-target verbs in v0.4 (the
`--concurrency` extension to bulk emits the same per-target
`data.results: [...]` envelope v0.3-M25 pinned; `item watch` is
**single-target streaming**, NOT multi-target — it emits one event
record per emitted NDJSON line, with the top-level envelope
covering the watch session itself). The shared per-target dispatch
helper (`dispatchSequential` in `src/api/partial-success-mutation.ts`,
lifted in v0.2) extends with a `dispatchConcurrent` sibling sharing
the same per-target id-field + `foldAndRemap` context — no §6.1
revision. v0.4 introduces no contract revision to §6.1.

**Out of scope (deferred per `cli-design.md` §13 + carried over from
v0.3 deferrals):**

- Full `doc` CRUD (`create`/`update`/`delete`) — v0.4 lands read-only
  per §13 v0.4 entry; full CRUD deferred to v0.5.
- Multi-level subitem creation — v0.3-M28 closed Decision 11 on
  empirical grounds (Monday's `sub_items_board` carries no
  `subtasks` column at API `2026-01`). Re-probe before any v0.4
  reopening; if the data model still doesn't surface deeper nesting,
  slips to v0.5 contingent on Monday's API evolution.
- OAuth app registration (`monday auth login`) — v0.3.0 ships with
  the M28 placeholder guard. Reopens only on clear user demand for
  browser-based login over `MONDAY_API_TOKEN`; not a v0.4 deliverable
  by default.
- Boolean filter DSL — v0.4 keeps the v0.1/v0.2 `--where` operator
  allowlist + `--filter-json`. Pencilled at v0.4 stretch / v0.5
  firm; only ships when fixture-driven adoption metrics show
  concrete demand.
- Deterministic pagination resume (`--resume <token>`) — cli-design
  §14.6 open question. Not a v0.4 candidate without explicit
  contract-change PR.
- `monday item recreate-from-archive` — still no misleading
  `restore` command (cli-design §5.4 stands as a permanent
  non-goal-adjacent decision).

**Permanent non-goals (per cli-design §13 — reminded here so plan
readers don't propose them as v0.4 candidates):**

- Hosting webhooks (CLIs can't expose public HTTP — out of model);
  v0.3's `webhook create` is the *registration* shape against
  Monday, not a receive endpoint. `item watch` is **agent-driven
  polling**, NOT a hosted webhook receiver.
- App framework / installable monday apps (different surface area).
- Real-time GraphQL subscriptions (Monday's endpoint doesn't
  support them) — `item watch` polls; the cadence pre-flight pins
  the polling burn vs freshness trade-off explicitly.
- Telemetry, update-notifier, analytics — ever.
- Forms (Monday's public-submission feature) — same hosted-
  endpoint shape as webhooks.
- Saved queries / aliases — would silently change behavior across
  machines; shell aliases / shell functions are the established
  UNIX answer.
- `monday undo` (replay-based reversal of recent mutations) —
  Monday's state model is authoritative and concurrent; honest
  substitutes are `--dry-run` (v0.1) and `item history` (v0.3-M24).

## 3. Milestone sequencing

v0.4 opens with **M29 — `item watch`** as the first milestone. The
remaining v0.4 milestones (a `--concurrency` extension, asset
upload, `doc` read-only, `team` writers, shell completion, and a
release-prep milestone closing 0.4.0) are sequenced incrementally as
each pre-flight runs. The first session opens the doc with §1 + §2 +
§3 opener + the M29 entry only; subsequent v0.4 pre-flight sessions
add M30, M31, etc. with their own entries here.

Order at a glance:

```
       M29                                — item watch (polling + circuit breaker)
       M30                                — --concurrency on item update --continue-on-error (bounded parallel partial-success bulk)
       M31 ─ ...                          — TBD as later milestones get pre-flighted
```

Each milestone is a coherent commit cluster (3–10 commits) ending on
a green tree with the listed exit criteria met. Earlier milestones
unblock later ones; do not start M(N) until M(N-1)'s exit criteria
are satisfied. Each milestone updates `docs/output-shapes.md` for any
new command shapes it lands and adds envelope snapshots for any new
emitted shape.

**Why this goes first.** Three reasons: (1) **Smallest v0.4
surface.** `item watch` adds one verb + one new module + one
streaming envelope shape; the multipart upload path (assets) and
the per-account concurrency probe (`--concurrency`) both touch
more existing infrastructure with more pre-flight risk.
(2) **Pre-trodden ground.** The M24 `item-history-projection.ts`
projector already emits the event shape `item watch` streams;
M29's runtime is "loop + project + emit" against an existing
projector, not a from-scratch event taxonomy. v0.3-M22's NDJSON
streaming + signal-handling discipline applies directly. (3) **No
dependency on later v0.4 surfaces.** `item watch` doesn't need the
`--concurrency` bulk extension (single-item watch), doesn't need
the multipart upload path (read-only stream), doesn't need `doc`
or `team` writers, doesn't need shell completion. Any other v0.4
candidate going first would either depend on an empirical probe
(asset multipart shape, `concurrency_exceeded` envelope at API
`2026-01`, `docs` query stability, `team` writer permissions) that
hasn't run yet OR would strand the v0.1-deferred reactivity
primitive indefinitely. M29 mirrors v0.3-M22's diagnostics-cluster
sizing — well-bounded, clear pre-flight question, single dominant
design decision.

**Pre-flight design clearance — closed at pre-flight contract
diff.** All eight clearance items closed at the M29 pre-flight
contract diff per the §8 D1–D5 closures below + the cli-design
§14.4 closure at `31713fb`. Verbatim closures:

1. **Polling cadence default + override — CLOSED.** Fixed 30s
   default (`DEFAULT_WATCH_INTERVAL_MS`) with `--interval <ms>`
   override; range 1000ms–3600000ms. Empirical-probe-pinned:
   per-poll cost is 10 complexity points against Monday's
   1,000,000/min budget — 30s burns 0.002%, so `daily_limit`
   (writes-only at API `2026-01`; doesn't apply to reads) is
   irrelevant + politeness + Monday's documented >30s
   `activity_logs` propagation lag (M24 finding 2026-05-11) are
   the binding constraints. The "10% of daily budget" framing in
   the original clearance was misframed against `daily_limit`;
   the closure replaces it with the per-minute complexity-budget
   math. Options (b) exponential-backoff-by-default + (c)
   Monday-signal-driven adaptive cadence rejected — adaptive
   shapes belong in v0.5+ if a v0.4-M29 user surfaces a real-
   world friction point.
2. **Circuit-breaker shape — CLOSED.** Reactive on Monday's
   `complexity_exceeded` / `concurrency_exceeded` /
   `rate_limited`. Respect `reset_in_x_seconds` (60s default
   when absent; 300s ceiling — `MAX_BACKOFF_SECONDS`). Trip
   after 5 consecutive failed polls
   (`CIRCUIT_BREAKER_CONSECUTIVE_FAILS`). Per-failure
   `WatchSessionWarning` records accumulate in-session and emit
   in the trailer's `_meta.warnings` slot (NOT interleaved with
   event lines per §6.3 streaming contract).
3. **Output envelope shape — CLOSED.** Each emitted line is a
   single JSON event record matching v0.3-M24's `item-history-
   projection.ts` `historyEvent` shape verbatim — NO additional
   `meta.emitted_at` slot (the M24 projector's `created_at` is
   the chronological key + the trailer-meta's `retrieved_at`
   carries session-end wall-clock). The session-level envelope
   wraps the stream: success at session end (on `--max-events`
   reach, on `--max-duration` reach, on `--once` drain, on
   SIGINT graceful drain); failure on circuit-breaker trip or
   non-recoverable Monday error. Trailer-meta carries the seven
   M29-specific slots per D3 below.
4. **Concurrency cap interaction — CLOSED (D4).** Each
   invocation independent (no shared registry); aligns with
   cli-design §3.1 #5.
5. **Exit semantics on signal — CLOSED.** SIGINT/SIGTERM
   triggers a graceful drain: in-flight poll completes or
   aborts cleanly via the AbortController seam (`ctx.signal`
   threaded into the polling loop, mirroring v0.3-M22's
   `monday status` probe's signal-handling pattern); trailer-
   meta emits as a final NDJSON line; exit 130 per §7. No
   special shutdown delay.
6. **`--once` flag — CLOSED (D2).** Distinct from
   `--max-events 1`. `--once` drains the backlog from `--since`
   (or the most-recent {@link DEFAULT_ONCE_BACKLOG_LIMIT}=100
   events if `--since` absent) and exits without polling.
   `--max-events 1` waits for the NEXT event.
7. **`--since <event-id>` for restartability — CLOSED.** Accepts
   the `last_seen_event_id` value from a prior session's
   trailer-meta. Runtime looks up the event-id → `created_at`
   once at startup, sets the initial poll-from timestamp. NOT a
   full `--resume <token>` state-machine resume (cli-design
   §14.6 stays open).
8. **`--include <kind1>,<kind2>` filter — CLOSED (D5).** Accepts
   the M24 closed 9-kind enum verbatim (`update_column_value` /
   `create_column` / `create_group` / `update_board_name` /
   `update_board_nickname` / `board_workspace_id_changed` /
   `update_posted` / `update_replied` / `unknown` — NOT the
   `item.created` / `item.column_changed` / `update.created`
   prefixes the original clearance speculated about; the M24
   probe's actual taxonomy is verb-shaped, not dotted). Applied
   at projection time; default = all kinds emitted. v0.4-M29
   polls `activity_logs` only, so `update_posted` /
   `update_replied` are valid argv values but emit no events at
   v0.4 (forward-compat for v0.5+ comment-polling).

  circuit_breaker_armed / unknown_event_kind) accumulate on

- **Behavioural ambiguity at pre-flight surfaces as P1s at
  IMPL.** Both round-1 P1s (signal handling + `--once`

  logically consistent but didn't pin the exact runtime

  IMPL reviewer (with a runtime body in hand) sees them.

  pattern proactively at the next milestone where the test
  asserts behavior driven by a specific wire-variable
  value.
- **Deadline-aware sleep is cheaper than min-clamp loops.**
  Round-1 P2-2 surfaced two patterns: a `min(sleep,
  remainingMs())` approach (chosen) and a "shrink the
  ceiling, multi-step sleep" approach (rejected). The

  need a nested loop. The chosen pattern reuses cleanly
  when the next milestone needs a wall-clock-bounded
  long-running verb.

  asymmetry, M29's prose drift was straightforward (3
  rounds for cleanup of "pre-flight stub" / "once IMPL

  genuinely ambiguous.

  optional slots flat under `_meta`. Future streaming verbs
