# v0.4 implementation plan

> **Status:** plan, not contract. The binding contract is
> [`cli-design.md`](./cli-design.md). This document sequences the
> work needed to ship v0.4 of that contract; it doesn't redefine it.
> If a conflict arises, `cli-design.md` wins and this plan is updated.

## 1. Scope summary

v0.4 is "**polish + nice-to-haves** — agents *react* and *attach*,
not just *narrate* and *write*." v0.3 closed the v0.1/v0.2 narration
gap (cross-board reads, item history, partial-success bulk) and the
v0.1/v0.2 outbound-write gap (notifications, webhooks). v0.4 picks
up the remaining cli-design §13 v0.4 candidates: a polling-based
reactivity primitive (`item watch`) so agents can wait for state
changes without scripting their own polling loop, bulk throughput
via `--concurrency` against Monday's per-account concurrency cap,
asset upload (`add_file_to_column` / `add_file_to_update`) so an
agent can attach evidence to its writes, read-only `doc list/get`,
`team` create/manage to close the noun gap, and shell completion
(bash / zsh / fish) for the rare human user. None of these are
load-bearing for the agent-narration story v0.3 already shipped —
v0.4 is what an agent reaches for when the v0.3 surface isn't
enough, not what the agent needs to do its day-one job.

**In scope (from `cli-design.md` §13 v0.4 + Appendix B verb-noun
matrix):**

**Universal partial-success rule (cli-design §6.1 compliant — same
shape as v0.2/v0.3).** Multi-target verbs in v0.4 (the
`--concurrency` extension to bulk emits the same per-target
`data.results: [...]` envelope v0.3-M25 pinned; `item watch` is
**single-target streaming**, NOT multi-target — it emits one event
record per emitted NDJSON line, with the top-level envelope
covering the watch session itself). The shared per-target dispatch
helper (`dispatchSequential` in `src/api/partial-success-mutation.ts`,
lifted in v0.2) gains a `dispatchParallel` sibling at v0.4-M30
(in `src/api/parallel-dispatch.ts`); the partial-success-bulk
wrapper routes between them based on the `--concurrency` value
while both routes share the per-target id-field + `foldAndRemap`
context — no §6.1 revision. v0.4 introduces no contract revision
to §6.1.

**Out of scope (deferred per `cli-design.md` §13 + carried over from
v0.3 deferrals):**

- Full `doc` CRUD (`create`/`update`/`delete`) — v0.4 lands read-only
  per §13 v0.4 entry; full CRUD deferred to v0.5.
- Multi-level subitem creation — v0.3-M28 closed Decision 11 on
  empirical grounds (Monday's `sub_items_board` carries no
  `subtasks` column at API `2026-01`). Re-probe before any v0.4
  reopening; if the data model still doesn't surface deeper nesting,
  slips to v0.5 contingent on Monday's API evolution.
- OAuth app registration (`monday auth login`) — v0.3.0 ships with
  the M28 placeholder guard. Reopens only on clear user demand for
  browser-based login over `MONDAY_API_TOKEN`; not a v0.4 deliverable
  by default.
- Boolean filter DSL — v0.4 keeps the v0.1/v0.2 `--where` operator
  allowlist + `--filter-json`. Pencilled at v0.4 stretch / v0.5
  firm; only ships when fixture-driven adoption metrics show
  concrete demand.
- Deterministic pagination resume (`--resume <token>`) — cli-design
  §14.6 open question. Not a v0.4 candidate without explicit
  contract-change PR.
- `monday item recreate-from-archive` — still no misleading
  `restore` command (cli-design §5.4 stands as a permanent
  non-goal-adjacent decision).

**Permanent non-goals (per cli-design §13 — reminded here so plan
readers don't propose them as v0.4 candidates):**

- Hosting webhooks (CLIs can't expose public HTTP — out of model);
  v0.3's `webhook create` is the *registration* shape against
  Monday, not a receive endpoint. `item watch` is **agent-driven
  polling**, NOT a hosted webhook receiver.
- App framework / installable monday apps (different surface area).
- Real-time GraphQL subscriptions (Monday's endpoint doesn't
  support them) — `item watch` polls; the cadence pre-flight pins
  the polling burn vs freshness trade-off explicitly.
- Telemetry, update-notifier, analytics — ever.
- Forms (Monday's public-submission feature) — same hosted-
  endpoint shape as webhooks.
- Saved queries / aliases — would silently change behavior across
  machines; shell aliases / shell functions are the established
  UNIX answer.
- `monday undo` (replay-based reversal of recent mutations) —
  Monday's state model is authoritative and concurrent; honest
  substitutes are `--dry-run` (v0.1) and `item history` (v0.3-M24).

## 3. Milestone sequencing

v0.4 opens with **M29 — `item watch`** as the first milestone. The
remaining v0.4 milestones (a `--concurrency` extension, asset
upload, `doc` read-only, `team` writers, shell completion, and a
release-prep milestone closing 0.4.0) are sequenced incrementally as
each pre-flight runs. The first session opens the doc with §1 + §2 +
§3 opener + the M29 entry only; subsequent v0.4 pre-flight sessions
add M30, M31, etc. with their own entries here.

Order at a glance:

```
       M29                                — item watch (polling + circuit breaker)
       M30                                — --concurrency on item update --continue-on-error (bounded parallel partial-success bulk)
       M31                                — asset upload (item upload + update upload; first multipart transport extension)
       M32                                — doc list/get (read-only workdocs surface; first v0.4 verb against Query.docs)
       M33                                — shell completion (bash / zsh / fish via hand-rolled per-shell templates; commander 14.0.3 ships no completion machinery per the M33 D1 empirical probe; CLI-internal, no wire surface) — picked at post-M32 IMPL session 169b2bc, pre-flight in progress (this commit)
       M34 ─ ...                          — TBD (team writers needs an empirical-probe session first; v0.4 release-prep lands last)
```

Each milestone is a coherent commit cluster (3–10 commits) ending on
a green tree with the listed exit criteria met. Earlier milestones
unblock later ones; do not start M(N) until M(N-1)'s exit criteria
are satisfied. Each milestone updates `docs/output-shapes.md` for any
new command shapes it lands and adds envelope snapshots for any new
emitted shape.

surface.** `item watch` adds one verb + one new module + one
streaming envelope shape; the multipart upload path (assets) and
the per-account concurrency probe (`--concurrency`) both touch

(2) **Pre-trodden ground.** The M24 `item-history-projection.ts`

design decision.

**Pre-flight design clearance — closed at pre-flight contract
diff.** All eight clearance items closed at the M29 pre-flight
contract diff per the §8 D1–D5 closures below + the cli-design
§14.4 closure at `31713fb`. Verbatim closures:

1. **Polling cadence default + override — CLOSED.** Fixed 30s
   default (`DEFAULT_WATCH_INTERVAL_MS`) with `--interval <ms>`
   override; range 1000ms–3600000ms. Empirical-probe-pinned:
   per-poll cost is 10 complexity points against Monday's
   1,000,000/min budget — 30s burns 0.002%, so `daily_limit`
   (writes-only at API `2026-01`; doesn't apply to reads) is
   irrelevant + politeness + Monday's documented >30s
   `activity_logs` propagation lag (M24 finding 2026-05-11) are
   the binding constraints. The "10% of daily budget" framing in
   the original clearance was misframed against `daily_limit`;
   the closure replaces it with the per-minute complexity-budget
   math. Options (b) exponential-backoff-by-default + (c)
   Monday-signal-driven adaptive cadence rejected — adaptive
   shapes belong in v0.5+ if a v0.4-M29 user surfaces a real-
   world friction point.
2. **Circuit-breaker shape — CLOSED.** Reactive on Monday's
   `complexity_exceeded` / `concurrency_exceeded` /
   `rate_limited`. Respect `reset_in_x_seconds` (60s default
   when absent; 300s ceiling — `MAX_BACKOFF_SECONDS`). Trip
   after 5 consecutive failed polls
   (`CIRCUIT_BREAKER_CONSECUTIVE_FAILS`). Per-failure
   `WatchSessionWarning` records accumulate in-session and emit
   in the trailer's `_meta.warnings` slot (NOT interleaved with
   event lines per §6.3 streaming contract).
3. **Output envelope shape — CLOSED.** Each emitted line is a
   single JSON event record matching v0.3-M24's `item-history-
   projection.ts` `historyEvent` shape verbatim — NO additional
   `meta.emitted_at` slot (the M24 projector's `created_at` is
   the chronological key + the trailer-meta's `retrieved_at`
   carries session-end wall-clock). The session-level envelope
   wraps the stream: success at session end (on `--max-events`
   reach, on `--max-duration` reach, on `--once` drain, on
   SIGINT graceful drain); failure on circuit-breaker trip or
   non-recoverable Monday error. Trailer-meta carries the seven
   M29-specific slots per D3 below.
4. **Concurrency cap interaction — CLOSED (D4).** Each
   invocation independent (no shared registry); aligns with
   cli-design §3.1 #5.
5. **Exit semantics on signal — CLOSED.** SIGINT/SIGTERM
   triggers a graceful drain: in-flight poll completes or
   aborts cleanly via the AbortController seam (`ctx.signal`
   threaded into the polling loop, mirroring v0.3-M22's
   `monday status` probe's signal-handling pattern); trailer-
   meta emits as a final NDJSON line; exit 130 per §7. No
   special shutdown delay.
6. **`--once` flag — CLOSED (D2).** Distinct from
   `--max-events 1`. `--once` drains the backlog from `--since`
   (or the most-recent {@link DEFAULT_ONCE_BACKLOG_LIMIT}=100
   events if `--since` absent) and exits without polling.
   `--max-events 1` waits for the NEXT event.
7. **`--since <event-id>` for restartability — CLOSED.** Accepts
   the `last_seen_event_id` value from a prior session's
   trailer-meta. Runtime looks up the event-id → `created_at`
   once at startup, sets the initial poll-from timestamp. NOT a
   full `--resume <token>` state-machine resume (cli-design
   §14.6 stays open).
8. **`--include <kind1>,<kind2>` filter — CLOSED (D5).** Accepts
   the M24 closed 9-kind enum verbatim (`update_column_value` /
   `create_column` / `create_group` / `update_board_name` /
   `update_board_nickname` / `board_workspace_id_changed` /
   `update_posted` / `update_replied` / `unknown` — NOT the
   `item.created` / `item.column_changed` / `update.created`
   prefixes the original clearance speculated about; the M24
   probe's actual taxonomy is verb-shaped, not dotted). Applied
   at projection time; default = all kinds emitted. v0.4-M29
   polls `activity_logs` only, so `update_posted` /
   `update_replied` are valid argv values but emit no events at
   v0.4 (forward-compat for v0.5+ comment-polling).

  `src/api/multipart-transport.ts` (NOT extension of
  `transport.ts`). The existing `Transport` interface's
  `body: JSON.stringify(...)` + `Content-Type: application/
  json` invariants don't compose with multipart's
  FormData-driven boundary. The new `MultipartTransport`
  interface mirrors `Transport`'s shape but with a binary
  `file: Blob` slot + `filename` slot; header lockdown
  carries over (`Authorization` + `API-Version` transport-
  owned; `Content-Type` set by `fetch` from FormData).

- **D5: Dry-run shape.** Argv-derived planned-operation
  envelope. `--dry-run` reads the file's local size via
  `fs.stat()` so the planned-change carries `file_size_bytes`
  (an agent can confirm the planned upload fits any known
  plan-tier ceiling before issuing the live mutation). No
  file bytes transmitted on dry-run. `meta.source: 'none'`.

- **D6: Cache invalidation.** `item upload` invalidates the
  parent item's board metadata cache on success (single-leg
  per §8 — the file column's `FileValue` ColumnValue is part
  of the cached board metadata projection). `update upload`
  does NOT invalidate (Updates aren't part of §8 cache scope).
  Read-side asset verbs (`monday item assets <iid>`,
  `monday update assets <uid>`) deferred to v0.4.x — see D6
  closure rationale below.

- **D7: ERROR_CODES.** No new top-level codes (29 stays).
  Failures route through `usage_error` (file path issues,
  oversize), `unsupported_column_type` (non-`file` column),
  `not_found` (item/update/column gone),
  `validation_failed` (Monday server-side reject), `forbidden`
  / `unauthorized` (token scope). Per-failure discrimination
  via `details.reason` slots (`file_not_readable`,
  `file_empty`, `file_too_large`).

- **D8: Idempotency.** NO. Each successful upload mints a
  fresh `Asset` with a new ID. Agents needing register-once
  semantics pre-read `Item.assets` (out of M31 scope; v0.4.x
  may add a `monday item assets <iid>` read verb).

- **D9: Output envelope.** `data.asset: {Asset}` (Monday's
  full 10-field projection: `id` / `name` / `url` /
  `public_url` / `file_extension` / `file_size` /
  `created_at` / `uploaded_by` / `original_geometry` /
  `url_thumbnail`) + echoed inputs (`item_id` / `column_id`
  / `filename` / `file_size_bytes` for `item upload`;
  `update_id` / `filename` / `file_size_bytes` for
  `update upload`). Echoed inputs let an agent confirm what
  was sent from one envelope read; the wire `asset` is
  Monday's full view of the uploaded record.

- **D10: File-path resolution.** Positional `<file>` is a
  local path resolved relative to cwd. **Stdin (`-`) is NOT
  supported in v0.4-M31** — a future contract extension may
  add stdin support once a `--filename <name>` companion
  flag is pinned (no `Asset.name` source when reading from
  stdin). Same shape as v0.1's `--body-file -` pattern
  (cli-design §4.4) but inverted — `<file>` is positional,
  not a flag value, because the upload verbs are file-first
  by nature.

- **D11: Operation-name + named-operation parity (R-NEW-37
  W2).** `AddFileToColumn` for `mutation { add_file_to_
  column(...) }`; `AddFileToUpdate` for `mutation
  { add_file_to_update(...) }`. Operation names pinned
  literally at the fetcher boundary; NOT caller-overridable
  (per the M27 round-1 P2-1 lesson — caller-overridable
  operation names are an unsafe-by-construction shape).

**Decisions (D1-D11) — all closed inline at the M32 pre-flight
contract diff.**

- **D1: Verb shape.** Two new dedicated read-only verbs (`monday
  doc list` + `monday doc get`). NOT extending an existing
  noun — `doc` joins as a new top-level noun (§4.1 already
  lists `doc` as the noun namespace pinned for v0.4). List
  with optional `--workspace <wid>,...` filter + `--order-by`
  + page/limit pagination; get with positional `<did>`.

- **D2: Wire type naming — `Document` vs `Doc`.** Monday's
  GraphQL type is `Document` (probe-confirmed; the standalone
  `Doc` type does NOT exist on the schema at API `2026-01`).
  CLI verb namespace is `doc` per cli-design §4.1; the
  `src/api/` module is named `documents.ts` (plural-noun
  convention mirroring `notifications.ts` / `webhooks.ts`);
  exported types use Monday's wire names verbatim (`Document`
  / `DocumentBlock`) so the wire-vs-CLI mapping is
  self-documenting. The CLI envelope carries `data.documents:
  [Document]` (list) and `data: <Document with blocks>` (get).

- **D3: Pagination — page/limit, not cursor.** Monday's
  `Query.docs(...)` accepts `limit: Int` (default `25` per the
  schema description) + `page: Int` (1-based). No cursor on
  the workdocs surface. CLI ceilings `--limit` at
  `MAX_DOC_LIST_LIMIT = 100` (`MIN_DOC_LIST_LIMIT = 1`,
  `DEFAULT_DOC_LIST_LIMIT = 25`) to keep worst-case response
  sizes bounded; Monday's wire has no documented hard cap but
  rich-text Documents are payload-heavy. Out-of-range argv
  rejects at parse boundary with `usage_error` (no wire call
  fires).

- **D4: `--workspace <wid>,...` filter.** Maps to wire
  `workspace_ids: [ID]`. Comma-separated input shape (matches
  the established `monday workspace add-users --users`
  pattern); per-entry WorkspaceIdSchema-branded validation
  inside the command's action body. Inaccessible workspace
  IDs surface as empty filter results — Monday's wire
  silently drops unknown IDs rather than rejecting the call;
  the CLI does NOT fire a resolver warning for inaccessibility
  because the wire doesn't distinguish "no docs in workspace
  X" from "X not accessible". Documented as a best-effort
  filter; agents that need workspace-membership confirmation
  read `monday workspace list` first.

- **D5: `--order-by <created_at|used_at>` argv.** Closed
  2-value literal-union enum pinned from the probe of
  `DocsOrderBy`. Default `'created_at'` (matches Monday's wire
  default at API `2026-01`). Both values sort `desc`
  server-side; Monday's wire has no ASC variant — agents that
  need ascending sort reverse the projection client-side.
  Unknown values reject at parse boundary with `usage_error`.

- **D6: `blocks` slot — `doc get` only.** `doc list` envelope
  ships the 13-field base Document WITHOUT the `blocks`
  selection (list-row projection — including rich-text bodies
  in a list multiplies payload across the page). `doc get`
  envelope ships the full 14-field Document with `blocks:
  [DocumentBlock]` hydrated. A future `monday doc list
  --with-blocks` flag is NOT in v0.4 scope; agents that need
  bulk-block reads loop `doc get` per ID.

- **D7: Cache invalidation — N/A.** Both verbs are read-only;
  no mutation surface, no cache invalidation. Cache layout:
  NO local cache for docs. Mirrors `monday usage` (M22),
  `monday status` (M22), `webhook list` (M27) — diagnostics /
  volatile surfaces don't cache. Workdocs are content-heavy +
  frequently human-edited; the stale-cache risk outweighs the
  cache-hit value. Output `meta.source: "live"`,
  `meta.cache_age_seconds: null` on every invocation.

- **D8: ERROR_CODES — 29 stays.** No new top-level codes.
  Failures route through existing codes:
  - `not_found` — `doc get <did>` against a non-existent or
    inaccessible doc ID. Monday's wire returns an empty `docs`
    array for both cases; the CLI surfaces both as
    `not_found` with `details.doc_id` (no `forbidden` rewrap
    — Monday's wire collapses the cases into the same shape).
  - `usage_error` — out-of-range `--limit` / `--page`,
    malformed `--workspace`, unknown `--order-by` value.
    Caught at parse boundary BEFORE any wire call.
  - `validation_failed` — Monday-side rejection (very rare
    for reads; included for completeness).
  - `forbidden` / `unauthorized` — token lacks workdoc read
    scope.

- **D9: Output envelope.** `doc list`: wrapped record
  `data: { documents: [Document], page, limit, returned_count,
  has_more }`. NOT a bare array — page/limit pagination
  surfaces pagination context inline rather than via
  `meta.cursor` (which is reserved for `items_page`-style
  cursor surfaces per §6.1). `has_more` is the
  `returned_count === limit` heuristic — Monday's wire
  doesn't surface a total count, so "exactly limit rows
  returned" is the only signal that a follow-up page may
  exist. `doc get`: direct unwrap `data: <Document with
  blocks>` matching the read-one-verb convention (`board
  get` returns `data: <Board>`, `user get` returns
  `data: <User>`). The Document's own `id` field is the
  echoed input — no separate `doc_id` slot.

- **D10: Operation-name + named-operation parity (R-NEW-37
  W2).** `ListDocs` for `query ListDocs(...) { docs(...) }`;
  `GetDoc` for `query GetDoc($ids: [ID!]!) { docs(ids:) }`.
  Both operationNames pinned literally inside the fetcher
  functions; NOT caller-overridable (per the M27 round-1 P2-1
  + M31 D11 closure — caller-overridable operationName slots
  are an unsafe-by-construction shape).

- **D11: `DocId` brand.** New numeric-string brand
  `DocIdSchema` in `src/types/ids.ts`. Monday's `Document.id`
  is `ID!` on the wire (numeric on every observed account at
  API `2026-01`; empirical probe Step 1). Brand keeps `DocId`
  distinct from `BoardId`/`ItemId`/etc. so the type system
  catches mismatches at compile time.

- **D1 — Polling cadence default + circuit-breaker shape.**
  **Closed:** default cadence 30s with `--interval <ms>` override
  (1000ms–3600000ms range). Per-poll cost is stable at 10
  complexity points against Monday's 1,000,000/min budget — 30s
  burns 0.002% of the per-minute budget; politeness + Monday's
  documented >30s `activity_logs` propagation lag (M24 probe)
  are the binding constraints, NOT budget. Circuit breaker is
  REACTIVE on Monday's `complexity_exceeded` /
  `concurrency_exceeded` / `rate_limited` wire errors;
  backoff respects `reset_in_x_seconds` (60s default cap; 300s
  ceiling); trip to failure envelope after 5 consecutive failed
  polls (`CIRCUIT_BREAKER_CONSECUTIVE_FAILS`). Per-failure
  `WatchSessionWarning` records append to
  `WatchItemResult.warnings`; the action body folds them into
  the trailer's standard `_meta.warnings[]` slot at exit per
  cli-design §6.3 (resource lines + final `_meta`; NO
  interleaving with event records). **No new ERROR_CODE** —
  the three existing rate-limit codes cover the circuit-
  breaker exit; trailer-meta `circuit_broken_at` slot + the
  underlying Monday error discriminate the trip mode.
- **D2 — `--once` vs `--max-events 1` semantics.** **Closed:**
  ship both as DISTINCT shapes. `--once` drains backlog from
  `--since` (or recent N events) and exits without polling;
  `--max-events 1` waits for the NEXT event. Collapsing them
  would surprise — `--once` is "what changed since I last
  looked?"; `--max-events 1` is "wake me on the next change".
- **D3 — Session-summary trailer schema.** **Closed:** seven
  M29-specific slots (`events_emitted` + `polls_made` +
  `failed_polls` + `watch_duration_seconds` +
  `last_seen_event_id` + `circuit_broken_at` + `exit_reason`)
  on top of the standard §6.3 streaming trailer shape. Note:
  the trailer's `warnings[]` slot is the standard §6.3
  `Warning[]` channel (NOT one of the seven M29-specific
  slots); session warnings (poll_failed /
  circuit_breaker_armed / unknown_event_kind) accumulate on
  `WatchItemResult.warnings` and the action body folds them
  into `_meta.warnings` at session end.
  `exit_reason` discriminates trailer interpretation
  (`max_events` / `max_duration` / `once_complete` / `signal` /
  `circuit_broken`); see output-shapes.md `item watch` entry +
  cli-design §4.3 row.
- **D4 — Multi-watcher concurrency policy.** **Closed:** each
  invocation independent; no shared registry; last-seen-event-id
  watermark lives in-memory only. Aligns with cli-design §3.1
  #5 ("agents do their own parallelism, CLI is per-invocation").
  Two concurrent watchers double the poll volume against Monday;
  agents that need N watchers spawn N processes.
- **D5 — `--include` enum closure.** **Closed:** accepts the M24
  closed 9-kind enum verbatim (`update_column_value` /
  `create_column` / `create_group` / `update_board_name` /
  `update_board_nickname` / `board_workspace_id_changed` /
  `update_posted` / `update_replied` / `unknown`). No M24
  taxonomy extension at M29. v0.4-M29 polls `activity_logs`
  ONLY, so `update_posted` / `update_replied` are valid argv
  values but emit no events at v0.4 (those synthesized kinds
  come from the M24 `updates` source which v0.4-M29 doesn't
  poll). Forward-compat for v0.4-stretch / v0.5 comment-polling
  is the design intent — extending to `--include-comments`
  later doesn't require an argv-surface revision.

### Lessons for the next milestone

- **The "non-retryable rewrap placement" pattern is unique to
  introducing a new transport that uses an existing retry layer.**
  Round-1 P2-1 caught a real runtime correctness issue — the
  `file_too_large` rewrap had to live INSIDE the retry thunk, not
  outside, because the underlying error class (`network_error` from
  the multipart transport's JSON-parse failure on HTML 413) is
  retryable while the rewrap's typed surface (`usage_error`) is
  non-retryable. The JSON path doesn't have this shape because
  Monday's wire surface returns typed errors directly via
  `mapResponse`; the multipart path can land in `network_error`
  before reaching the typed-rewrap layer. **Recommendation for
  future "new transport seam" milestones**: add a "non-retryable
  rewrap placement" check to R-v0.4-W2 — for any transport-level
  error that the milestone wants to rewrap as a typed user-facing
  error, verify the rewrap fires INSIDE the retry thunk so the
  resulting non-retryable error short-circuits the loop.
- **`fs.stat()` does NOT verify R_OK.** Round-1 P2-2 caught a
  pre-check gap that's easy to miss — `fs.stat()` confirms
  existence + type + size, but not read permission. Always pair
  with `fs.access(path, R_OK)` for any file the action will
  actually READ later. Same applies to write paths — `fs.access(path,
  W_OK)` ahead of `fs.writeFile(...)`. Add this to a future
  "pre-check discipline" rule in `.claude/rules/security.md` or
  `cli.md` if a 2nd consumer surfaces.
- **Cross-doc grep at IMPL kickoff (R-NEW-56) is now a 2nd-time
  validated discipline.** M30 IMPL's 5-round prose-drift cadence
  forced the discipline; M31 IMPL's 3-round convergence vindicated

  2" — it's "lift at 2 when the duplicated surface's branch-

  Carry forward.
- **3-round IMPL convergence is the new ceiling for "new
  transport seam" milestones at IMPL.** M27 IMPL's 4-round +

- **R-NEW-75 — Candidate-selection session shape for
  post-feature-cluster milestone picking** (1 supporting
  instance at post-v0.4-M32 IMPL — LOW priority watch-item,
  process discipline pattern; NOT a code lift). Surfaced at
  the post-M32 IMPL housekeeping session `169b2bc`
  (2026-05-14). The session prompt called out that the
  "candidate-selection" session has no historical precedent
  in this repo — every prior milestone's preceded-by session
  was either an empirical probe (v0.3-M21 OAuth / M22
  diagnostics / M23 favorites / M24-prep history-kinds / M27
  webhooks / v0.4-M32 docs) or a direct pre-flight kickoff.
  This was the first explicit "scope each remaining backlog
  candidate + recommend" session.

  **The shape:**

  1. **Confirm clean state** — `git status` + `git log
     --oneline -12` + `npm test --reporter=dot 2>&1 | tail -4`
     verify clean tree, unpushed cluster matches expectations,
     test suite green at HEAD.
  2. **Read each remaining backlog entry** from
     `docs/cli-design.md §13 v<X>` against the current state's
     "next milestone TBD" annotation in CLAUDE.md.
  3. **Scope each candidate against 5 dimensions:**
     - **Wire-shape novelty** — does it need an empirical
       probe before pre-flight?
     - **Transport seam** — does it introduce a new transport
       class? (See R-v0.4-W2 for the "new transport seam"
       interface-mirror checklist that fires at pre-flight.)
     - **Destructive gate** — does it ship verbs requiring
       `--yes` per cli-design §3.1 #7?
     - **R-class triggers** — does it crystallize a known
       2-consumer or 3-consumer R-class candidate per
       R-NEW-58's lift-ahead-of-feat discipline?
     - **Codex round estimate** — based on the M22 / M27 /
       M30 / M31 / M32 read-surface precedent (median 3 IMPL
       rounds at v0.4-plan §14 M32 post-mortem).
  4. **Recommend ONE candidate** with neutral trade-offs
     presented; do NOT pick silently if the choice is
     non-obvious (per the project's "don't pick silently"
     discipline at CLAUDE.md "Workflow rules").
  5. **Ask the user** via `AskUserQuestion` for the binding
     decisions (push the unpushed cluster? + pick the
     candidate?) — single round-trip rather than two
     plain-text approval cycles.
  6. **Annotate `CLAUDE.md` "Next session" block** with the
     picked candidate + commit
     `docs(m<N>-prep): annotate Next session block — M<N> = <candidate>`
     + push the cluster.

  **Why it stays as discipline rather than tooling/code:**
  the framework itself is the load-bearing piece — the
  5-dimension scoping is what makes the recommendation
  non-arbitrary. The session itself is small (single AskUser
  round-trip + one doc commit + one push); codifying as a
  script would over-engineer a once-per-feature-cluster
  ritual. The framework cost is in REMEMBERING to scope
  against all 5 dimensions rather than picking based on
  one (typically "smallest first" or "newest interest"),
  which is what makes a written watch-item worthwhile.

  **Watch-item fires at 2nd consumer** — any future
  post-feature-cluster decision point where multiple
  candidates remain with non-obvious priority. Likely
  v0.4 candidates: post-M33 IMPL when team-writers vs
  release-prep needs choosing (but with only 2 candidates
  remaining, the choice may be obvious enough to skip the
  dedicated session). Likely v0.5 candidate: v0.5 kickoff
  with the doc-CRUD-mutation backlog (9 surfaces per the
  M32 D8 closure — `create_doc` / `update_doc_name` /
  `delete_doc` / `duplicate_doc` / `import_doc_from_html` /
  `add_content_to_doc_from_markdown` / `create_doc_block` /
  `update_doc_block` / `delete_doc_block`).

  **Graduation criteria:** if the 2nd consumer fires AND
  uses the 5-dimension framework verbatim, R-NEW-75
  graduates to a permanent CLAUDE.md "Workflow rules"
  addition. If the 2nd consumer drifts the dimensions
  (e.g., needs a 6th axis for a v0.5 surface class that
  doesn't fit one of the 5 today), document the drift
  here + keep as watch-item.
