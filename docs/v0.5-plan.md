# v0.5 implementation plan

> **Status:** plan, not contract. The binding contract is
> [`cli-design.md`](./cli-design.md). This document sequences the
> work needed to ship v0.5 of that contract; it doesn't redefine it.
> If a conflict arises, `cli-design.md` wins and this plan is updated.

## 1. Scope summary

v0.5 is "**writers + workdocs CRUD** — agents *create* and *edit*
people-structure and document content." v0.4 closed the
**reactivity** (`item watch`), **bulk throughput** (`--concurrency`),
**asset upload** (multipart wire), **read-only docs** (`doc list/get`),
and **shell completion** gaps. v0.5 picks up the remaining cli-design
§13 v0.5 candidates: the deferred-from-v0.4-M34 **team writer**
surface (create / update / delete / add-users / remove-users) and the
**full workdocs CRUD** mutation backlog Monday exposes on the wire
(9 doc-mutation surfaces deferred from v0.4-M32's read-only landing).
Bundled together at the post-v0.4-M33 candidate-selection session
(R-NEW-75 graduation) for a coherent "team + docs CRUD" v0.5 frame
rather than splitting them across releases.

**In scope (from `cli-design.md` §13 v0.5 + Appendix B verb-noun
matrix):**

| Group | Commands |
|-------|----------|
| **team writers** | `monday user team-list`, `monday user team-get <tid>`, `monday user team-create --name <n> [--users <id>,...] [--guest-team] [--parent <ptid>] [--allow-empty]`, `monday user team-delete <tid> --yes`, `monday user team-add-members <tid> --users <id>,...`, `monday user team-remove-members <tid> --users <id>,...`. Monday's mutation surface (v0.5 kickoff probe `scripts/probe/v0.5-team-mutations.ts` 2026-05-15, API `2026-01`): `create_team(input: CreateTeamAttributesInput!, options: CreateTeamOptionsInput) → Team` + `delete_team(team_id: ID!) → Team` + `add_users_to_team(team_id, user_ids: [ID!]!) → ChangeTeamMembershipsResult` + `remove_users_from_team(team_id, user_ids: [ID!]!) → ChangeTeamMembershipsResult`. **No `update_team` mutation exists** — Monday provides no rename / re-describe surface for teams (drop the `--description` flag the v0.4 cli-design row pencilled — `Team` object carries no description field on the wire). **Out-of-scope tangential verbs probe-surfaced**: `assign_team_owners` / `remove_team_owners` (owner-vs-member distinction); `add_teams_to_board` / `delete_teams_from_board` (board subscription, BoardSubscriberKind); `add_teams_to_workspace` / `delete_teams_from_workspace` (workspace subscription, WorkspaceSubscriberKind). **Universal partial-success rule (cli-design §6.1 compliant — same
shape as v0.2/v0.3/v0.4).** Multi-target verbs in v0.5 (the
`team-add-members` / `team-remove-members` verbs emit per-target
results when multiple users are passed) reuse the shared per-target
dispatch helper (`dispatchSequential` in
`src/api/partial-success-mutation.ts`, lifted in v0.2). v0.5
introduces no contract revision to §6.1; the team-membership verbs
follow the same envelope shape v0.3-M19 `monday workspace add-users`
pinned.

**Out of scope (deferred per `cli-design.md` §13 + carried over from
v0.4 deferrals):**

- Files-shaped friendly `--set` translator + `--set-raw` form for
  file columns — slipped from v0.4 release-prep; would need a
  separate dispatch from the translator boundary into the multipart
  wire. Re-evaluate at v0.5 mid-cluster or slip to v0.5.x.
- Cross-board `item move` value-overrides — slipped from v0.3-M28
  audit, then again from v0.4 release-prep. Monday's
  `ColumnMappingInput` carries no value slot at API `2026-01`; the
  richer `{id, value?}` form requires a non-atomic post-move
  `change_multiple_column_values` with cross-leg partial-failure
  envelope shapes. Out of v0.5 scope unless Monday's API surfaces
  the slot at a newer version.
- Cross-board search resumable cursor — slipped from v0.4
  release-prep; per-board cursor-lifetime under aggregation remains
  the load-bearing design issue. Not a v0.5 candidate.
- Multi-level subitem creation — slipped from v0.4 release-prep;
  conditional on Monday's data model surfacing `subtasks` on
  `sub_items_board` at API `2026-01`+. Re-probe empirically before
  any v0.5 reopening; otherwise slips to v0.6.
- OAuth app registration (`monday auth login`) — v0.4.0 still ships
  with the M28 placeholder guard. Reopens only on clear user demand
  for browser-based login over `MONDAY_API_TOKEN`; not a v0.5
  deliverable by default.
- Boolean filter DSL — kept the v0.1/v0.2 `--where` operator
  allowlist + `--filter-json` through v0.4. Pencilled at v0.5
  stretch; only ships when fixture-driven adoption metrics show
  concrete demand.

**Permanent non-goals (per cli-design §13 — reminded here so plan
readers don't propose them as v0.5 candidates):**

- Hosting webhooks (CLIs can't expose public HTTP — out of model).
- App framework / installable monday apps (different surface area).
- Real-time GraphQL subscriptions (Monday's endpoint doesn't
  support them).
- Telemetry, update-notifier, analytics — ever.
- Forms (Monday's public-submission feature) — same hosted-
  endpoint shape as webhooks.
- Saved queries / aliases — would silently change behavior across
  machines; shell aliases / shell functions are the established
  UNIX answer.
- `monday undo` (replay-based reversal of recent mutations) —
  Monday's state model is authoritative and concurrent; honest
  substitutes are `--dry-run` (v0.1) and `item history` (v0.3-M24).

**Findings summary — load-bearing surprises:**

1. **`Mutation.update_team` DOES NOT EXIST.** cli-design §4.3
   pencilled an `--description <d>` flag on team-create; the
   wire surface offers neither rename nor re-describe. `Team`
   object also carries NO `description` field (6 fields only:
   `id` / `name` / `owners` / `picture_url` / `users` /
   `is_guest`). M34 contract diff drops the `--description`
   flag (no wire-side persistence) and no v0.5 `team-update`
   verb (no wire path).
2. **`create_team` takes two inputs:** `input:
   CreateTeamAttributesInput!` (`name!`, `is_guest_team`,
   `parent_team_id`, `subscriber_ids: [ID!]`) + `options:
   CreateTeamOptionsInput` (`allow_empty_team`). Hierarchical
   teams exist via `parent_team_id`; v0.5-M34 surfaces the
   slot but defers UX shaping to documentation only (no
   `--parent` flag at M34 — flag at v0.5.x if user demand
   surfaces).
3. **`add_users_to_team` / `remove_users_from_team`** return
   `ChangeTeamMembershipsResult { failed_users: [User!],
   successful_users: [User!] }` — a partial-success envelope at
   the WIRE level. This is the 2nd consumer of R-NEW-31's
   discriminated-union per-status-detail-schema pattern. The
   CLI's `team-add-members` / `team-remove-members` envelope
   wraps this into the §6.1 universal partial-success shape
   (`data.results: [{ ok, user_id, ... }]`) at the action
   boundary.
4. **`Query.teams(ids: [ID!])`** — NO `limit:`, NO pagination,
   NO cursor. Returns all teams in one shot when no `ids`
   passed. M34 contract diff documents the deferred pagination
   slot (Monday surface doesn't expose one) + the natural
   account-size cap on team lists.
5. **`User.teams` exists** (tangential read); `Account.teams`
   does NOT. M34 deferral: a future `monday user teams <uid>`
   verb has a wire path; pencilled at v0.5.x if user demand
   surfaces (not on M34's scope).
6. **9 doc mutations exist; names match handoff verbatim;
   return-type heterogeneity (5 distinct shapes):**
   - Full `Document`: `create_doc(location: CreateDocInput!)`
     — `CreateDocInput` is EITHER `board: CreateDocBoardInput
     { column_id!, item_id! }` (doc-on-column) OR `workspace:
     CreateDocWorkspaceInput { workspace_id!, name!,
     kind?: BoardKind, folder_id? }` (workspace-level doc).
     M35 contract diff branches the CLI argv into the two
     placement modes per D7 closure — two CLI verbs:
     `monday doc create-in-workspace --workspace <wid>
     --name <n> [--folder <fid>] [--kind <k>]` vs
     `monday doc create-on-column --item <iid> --column <cid>`.
   - Opaque `JSON` scalar: `update_doc_name(docId!, name!)`,
     `delete_doc(docId!)`, `duplicate_doc(docId!,
     duplicateType?: DuplicateType)`. CLI projects the JSON
     scalar into a flat `{ doc_id: string, success: true }`
     envelope at the fetcher boundary per D9 closure (`success`
     pinned literal-`true` — Monday surfaces failure via
     GraphQL `errors[]`, NOT via a wire-side success flag).
     Empirical IMPL cassette pins how Monday surfaces the
     opaque JSON payload (`duplicate_doc` carries the new
     doc's id; `rename` / `delete` likely surface `null` /
     empty record).
   - `OBJECT/DocumentBlock`: `create_doc_block(doc_id, type:
     DocBlockContentType!, content: JSON!, after_block_id?,
     parent_block_id?) → DocumentBlock` +
     `update_doc_block(block_id!, content: JSON!) →
     DocumentBlock`. Block returned in full.
   - `OBJECT/DocumentBlockIdOnly`: `delete_doc_block(block_id!)
     → { id }` — single-field return.
   - Custom `success/error` result: `import_doc_from_html(html!,
     workspaceId!, kind?: DocKind, folderId?, title?) →
     ImportDocFromHtmlResult { success!, doc_id?, error? }` +
     `add_content_to_doc_from_markdown(docId!, markdown!,
     afterBlockId?) → DocBlocksFromMarkdownResult { success!,
     block_ids?, error? }`. CLI maps `success: false` to
     `validation_failed` or `internal_error` per the wire
     `error` field's content.
7. **camelCase vs snake_case arg-name asymmetry across the 9
   doc mutations:** `update_doc_name` / `delete_doc` /
   `duplicate_doc` / `import_doc_from_html` /
   `add_content_to_doc_from_markdown` use **camelCase** args
   (`docId`, `afterBlockId`, `workspaceId`, `folderId`);
   `create_doc_block` / `update_doc_block` / `delete_doc_block`
   use **snake_case** (`doc_id`, `block_id`, `after_block_id`,
   `parent_block_id`). The wire-side inconsistency stays at the
   fetcher boundary; CLI argv lands in kebab-case throughout
   (snake_case in error details). **R-NEW-41 4th-consumer
   trigger fires** — see §22 R-class register.
8. **`DocBlockContentType` is a 16-value closed enum** for
   `create_doc_block.type`: `bulleted_list` / `check_list` /
   `code` / `divider` / `image` / `large_title` / `layout` /
   `medium_title` / `normal_text` / `notice_box` /
   `numbered_list` / `page_break` / `quote` / `small_title` /
   `table` / `video`. M36 contract diff pins the closed enum
   at the parse boundary. **Asymmetric typing note:** M32
   read-side `DocumentBlock.type` surfaces as plain `String`
   (not the enum) — write-side constrains, read-side relaxes.
   Another wire-vs-CLI semantics asymmetry (5th supporting
   site for R-NEW-41).
9. **`DuplicateType` 2-value enum** for `duplicate_doc`:
   `duplicate_doc_with_content` (content-only, default) /
   `duplicate_doc_with_content_and_updates` (full backup with
   comments + update history).
10. **NO async-job surface** for any doc mutation — all 9 are
    synchronous. **R-v0.4-W1 (`dispatchPollingLoop` helper)
    does NOT fire here.** Synchronous import behaviour at API
    `2026-01` may differ from older versions Monday's reference
    docs describe; the contract diff cites the empirical pin.
11. **`AssignTeamOwnersError` / `RemoveTeamOwnersError`** shape:
    `{ message, code: AssignTeamOwnersErrorCode, user_id }`.
    Per-user error discrimination on `assign_team_owners` /
    `remove_team_owners` — out of M34 scope (those mutations
    deferred per finding 1 above), but the error-code-enum-per-
    mutation pattern is a watch-item.
12. **6 tangential team-shaped mutations beyond the 4 core
    ones** (`assign_team_owners` / `remove_team_owners` /
    `add_teams_to_board` / `delete_teams_from_board` /
    `add_teams_to_workspace` / `delete_teams_from_workspace`).
    M34 explicitly scopes to the 4 core team-CRUD mutations

    regression).

    (Monday promises non-null `doc_id` / `block_ids` on success
    per probe descriptions).

    WITH empty `block_ids` (plausible "markdown had no
    convertible blocks" semantics on append-markdown; the

  layer can return the typed envelope). CLI mitigation: parse-
  boundary string-length check via

  last-known-good; UTF-8 byte count, NOT UTF-16 code units) on

  'htmlString'|'markdownString', message: '...exceeds the
