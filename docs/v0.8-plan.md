## 1. Scope summary

v0.8 is "**Monday API 2026-07 + user-entity migration**" — the
second of two API-version-bump releases pinning the CLI to API
`2026-07`. Unlike v0.7's broadly-additive 2026-04 surface, **2026-07
ships a focused user-entity restructure with multiple breaking
changes** (field type changes, deprecated `Query.users` args, a
1000-row hard cap on user pagination). v0.8's load-bearing work is
the user-entity contract migration, NOT new feature surface area —
the new wire surface (`users.activity_logs` + `user_configs`) is
secondary scope.

### M44 — User-entity contract migration

**Wire surface:** Existing `Query.users` + `User` shape — same wire
op, modified contract surface at the SDK + projection layer.

**Pre-IMPL cross-doc grep (R-NEW-72 graduated discipline):** Run
at kickoff to enumerate every consumer of the affected User
shape + Query.users args:

```bash
grep -rn '\bQuery\.users\b\|users\\b.*kind\\b\|newest_first\|non_active' src/ tests/ docs/
grep -rn '\bUser\.created_at\b\|\bUser\.birthday\b\|\bUser\.utc_hours_diff\b' src/ tests/ docs/
grep -rn 'user list --all\|user.*pagination' src/ docs/
```

**Empirical probe required at pre-flight:**

- Type-change probe — what TypeScript types does SDK 16.x ship
  for the three changed `User` fields (`created_at`, `birthday`,
  `utc_hours_diff`)? Was the change ISO-string ↔ Date object,
  string ↔ number, or something else? Drives the projection
  re-shape design.
- 1000-row cap probe — does Monday's `Query.users(limit: ...)`
  reject `limit > 1000` with `validation_failed`, or silently
  cap? Drives the `user list --all` warning shape.
- Deprecated-args behavior probe — do the three deprecated
  `Query.users` args (`kind`, `newest_first`, `non_active`)
  still function at API `2026-07`, or do they return
  `validation_failed`? Drives migration timing (graceful
  degradation with deprecation warning vs immediate removal).

**Open decisions at pre-flight:**

- **D1 — Type-change projection design.** Three sub-decisions
  (one per changed field) — each driven by the type-change probe
  results. Likely D1a / D1b / D1c at pre-flight.
- **D2 — Deprecated `Query.users` args handling.** Options:
  (a) Remove the CLI flags that consumed the deprecated args
      (clean break — agents update at v0.8 cutover).
  (b) Keep CLI flags but surface a deprecation warning + map to
      the non-deprecated equivalents at the wire boundary
      (graceful — agents migrate over the v0.8.x window).
  (c) Mark CLI flags as deprecated in `--help` but keep
      forwarding the args verbatim (Monday's deprecation warning
      surfaces); transition once Monday drops the args.
- **D3 — 1000-row cap warning shape.** `monday user list --all`
  needs to surface a warning when the requested page size +
  cumulative pagination would exceed 1000 rows. Warning shape:
  envelope-level `warnings: [{code: 'user_pagination_capped',
  ...}]` with `details.cap: 1000` + `details.hint` pointing at
  narrowing filters. Mirrors v0.3-M23's `cross_board_truncated`
  warning shape.
- **D4 — New `User` fields projection subset.** Which of the 10
  new 2026-07 `User` fields land in `monday user get` /
  `monday user list` projections? Likely: `account_id`,
  `status`, `photo_url`, `is_deleted`, `is_email_confirmed`
  (agent-useful). Skip: `serial_number`, `bb_visitor_id`,
  `became_active_at`, `invitation_method` (niche / internal) +
  `user_config` (deferred to v0.8.x candidate). Decision at
  M44 pre-flight.
- **D5 — ERROR_CODES delta.** Likely zero (registry stays at 29).
  Existing `validation_failed` covers cap violations + deprecated-
  arg rejections.

**IMPL Codex review estimate:** 3-5 fix-up rounds (contract surface
migrations are typically more invasive than feature adds — every
test cassette pinning the old User shape needs refreshing;
deprecation-warning shape design surfaces edge cases).

**R-class triggers anticipated:**

- Per-version contract-migration discipline — first major instance
  in the project's lifetime where an existing surface migrates
  (vs additive only). May surface a new R-NEW-X "wire-shape
  migration cluster pattern" at IMPL close.
- Pagination-cap warning helper potentially shared with v0.3-M23's
  `cross_board_truncated`. R-NEW-58 ahead-of-feat trigger fires
  only if the helper sees 3+ consumers (likely just 1 at M44 +
  the existing M23 consumer = 2; below threshold).

### M45 — `monday user activity <uid>`

**Wire surface:** `users.activity_logs` query — paginated
(cursor-based) with filters for board + event type. New query, no
prior CLI surface.

**Empirical probe required at pre-flight:**

- Wire-shape probe — what fields does `users.activity_logs[]`
  carry? Likely mirrors `boards.activity_logs` shape from v0.3-M24
  (`item history`); verify exact field set + per-event projection
  variants.
- Cursor lifetime probe — does Monday's standard 60-minute cursor
  lifetime apply, or does this surface ship a different lifetime?
  Drives the `stale_cursor` shape pin.
- Filter-decoder probe — what filter values does the wire accept
  (event type enums, board IDs, date ranges)?

**Open decisions at pre-flight:**

- **D1 — Reuse `--filter-json` DSL?** v0.1 / v0.3 ships the
  `--where <col>=<value>` + `--filter-json` shape; M45 likely
  reuses it for board / event-type / date filters. Decision at
  pre-flight after the filter-decoder probe.
- **D2 — Per-event projection (typed-discriminated-union pattern
  from v0.3-M24).** Reuse M24's per-event-type projection
  (`update_column_value` / `update_posted` / `update_replied`)
  + extend for any user-activity-specific event types (likely
  `user_login` / `user_status_changed` / `user_invitation_*`).
- **D3 — NDJSON output mode?** v0.4-M29 `item watch` ships NDJSON
  for long-poll streaming; `user activity` is paginated read, not
  long-poll. Decision: ship JSON envelope with cursor pagination
  (mirrors `item history`), NOT NDJSON. Confirmed at pre-flight.
- **D4 — ERROR_CODES delta.** Likely zero. `stale_cursor`
  (existing) covers the 60-minute cursor lifetime; `not_found`
  covers invalid `uid`; `usage_error` covers bad filter shapes.

**IMPL Codex review estimate:** 3-4 fix-up rounds (median IMPL
cadence; per-event projection design is the main risk).

**R-class triggers anticipated:**

- M24's per-event projection helper sees a 2nd consumer at M45;
  R-NEW-58 ahead-of-feat trigger fires only if a 3rd consumer is
  anticipated within v0.8 scope (none expected).

## 6. Risk register

> **Per-milestone risks land at each milestone's pre-flight
> kickoff.** Skeleton entries:

- **R1 — SDK 16.x publication timing.** Same shape as v0.7 R1 —
  if SDK 16.x baking `2026-07` is not published at v0.8 kickoff,
  the pin-bump decision tracks v0.7's. Mitigation:
  string-literal override on whatever SDK ships
  `2026-04` as a fallback.
- **R2 — User-entity migration blast radius.** The user surface
  is one of the project's oldest (v0.1) + most-used (referenced
  across `account whoami` / `user list` / `user get` / `user me`
  / team writers M34 / dev convention layer M26 + others).
  Cross-doc grep at kickoff enumerates the exact blast radius;
  IMPL fix-up cadence likely 4-5 rounds vs the 3-round median.
  Mitigation: aggressive pre-flight cross-doc grep + cassette
  refresh sweep + Codex-pre-flight-template W{N} audit-point
  for migration test parity.
- **R3 — Pagination-cap user-facing semantics.** `user list --all`
  is a v0.1 behavior; introducing a 1000-row cap warning is a
  contract-extending change (the envelope gains a new
  warning code). Mitigation: M44 D3's
  `user_pagination_capped` warning shape pins the contract at
  the cli-design §6.5 warning-shape registry; agents key off the
  warning code, never message text.
- **R4 — Deprecated-args graceful degradation timing.** Monday's
  deprecated-args timeline (do they reject at `2026-07` immediately
  or after a deprecation window) drives M44 D2's graceful-vs-clean-
  break decision. Mitigation: pre-flight probe + a "ship clean
  break, document migration in CHANGELOG upgrade-notes" default
  unless probe surfaces graceful path is materially better.
