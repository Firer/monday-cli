## 1. Scope summary

v0.7 is "**Monday API 2026-04 + carry-forward enrichments**" — the
first of two API-version-bump releases pinning the CLI to a newer
Monday API surface. v0.6 closed the files-shaped friendly `--set`
writer path (the longest-running v0.4 → v0.5 → v0.6 carry-over).
v0.7 picks up the next class of work: pinning to API `2026-04` (the
first GA Monday API version newer than `2026-01`) and exposing the
high-value additive surfaces that version introduces, while folding
in the v0.6.x bulk + create file-`--set` carve-outs deferred at M38.

### M41 — `monday doc block-create-bulk <did>`

**Wire surface:** `create_doc_blocks` mutation — bulk-create up
to 25 doc blocks per call. Closes the per-call efficiency gap in
M36's per-block CRUD (where N blocks = N round-trips).

**Empirical probe required at pre-flight:**

- Wire-shape probe — payload shape for the 25-block max. Likely
  an array of M36-shaped block records; verify exact shape +
  per-block error semantics (does a single bad block reject the
  whole batch, or does the wire return per-block partial
  success?). Probe drives the §6.1 envelope shape decision.

**Open decisions at pre-flight:**

- **D1 — Per-block partial-success vs all-or-nothing envelope
  shape.** If the wire returns per-block partial success
  (`failed_blocks` / `successful_blocks` similar to M34's team
  mutations), project to the universal §6.1 `data.results:
  [{block_index, ok, ...}]` shape. If all-or-nothing, return a
  flat success envelope with the created `blocks` array. Probe
  pins this.
- **D2 — Mutex with M36 `block-create`.** Single-block create stays
  on the M36 single-block verb; M41 is the bulk variant. Mirrors
  v0.3-M25 `update --where --continue-on-error` pattern where the
  bulk verb is orthogonal to the single-item one.
- **D3 — `--blocks <json>` parse-boundary size cap.** Per the M37
  pattern: pre-empt at parse boundary if the wire's max is fixed
  (25 blocks = some byte threshold). Probe pins the threshold.
- **D4 — ERROR_CODES delta.** Likely zero. Bulk-specific
  rejections route through `usage_error` / `validation_failed`
  with `details.reason: 'block_batch_too_large'` /
  `'block_validation_failed'` discriminators.

**IMPL Codex review estimate:** 3-4 fix-up rounds (one above median
— the partial-success projection design dimension typically
surfaces an extra fix-up round per v0.5-M34 precedent).

**R-class triggers anticipated:**
Per-batch partial-success projection (`projectBlockBatchResults`)
likely 1-2 consumers at M41 close; R-NEW-58 ahead-of-feat trigger
fires only if a 3rd consumer site is anticipated within v0.7 scope.

### M42 — Bulk file `--set` carve-out fold (D5 closure from v0.6-M38)

**Wire surface:** `add_file_to_column` per-item, dispatched across
the `--where`-resolved item-id set with the M25 partial-success
envelope. No new wire op; reuses v0.4-M31's multipart wire +
v0.6-M38's `executeFileColumnSet` runtime body verbatim.

**Empirical probe NOT required at pre-flight** (wire surface is
known + cassette-pinned at v0.4-M31; novelty is in the per-item
file dispatch + `--concurrency` interaction, which is
implementation work, not wire-shape work).

**Open decisions at pre-flight:**

- **D1 — `--concurrency` semantics for file dispatch.** Does
  `--concurrency 4` mean 4 parallel multipart uploads sharing the
  same MultipartTransport, or does each parallel leg get its own
  transport? Probe pinning the wire-side per-token rate limits at
  pre-flight + a design Decision.
- **D2 — Per-item asset slot in envelope.** Per-item `data.results[
  i].asset: { id, name, ... }` echo per the M31 success envelope,
  with per-item failure path landing as
  `data.results[i].error: { code, message, ... }` per M25 partial-
  success.
- **D3 — Per-item file pre-check timing.** File pre-checks (size,
  readability, mime-sniff) MUST fire before any wire round-trip
  per cli-design §5.8 atomicity discipline. Either pre-check ALL
  files synchronously before dispatching ANY, OR pre-check
  per-item just before its dispatch (parallel-safe). Decision
  drives whether a single bad file rejects the whole batch
  (--continue-on-error: NO) or just that item (`--continue-on-error`:
  YES).
- **D4 — ERROR_CODES delta.** Likely zero. Per-item failures route
  through existing codes with new `details.reason: 'file_not_
  readable_in_batch'` / `'file_empty_in_batch'` discriminators.

**IMPL Codex review estimate:** 4-5 fix-up rounds (one or two above
median — the partial-success + concurrency + multipart triangle
typically surfaces multiple design dimensions per round).

**R-class triggers anticipated:**

- `file-source.ts` `precheckLocalFile` consumer count goes 3 → 4
  (M31 item upload + M31 update upload + M38 item set + M42 bulk
  item update). R-v0.6-NEW-1 watch-item — already-shipped helper
  scales cleanly to consumer 4+.
- Per-item file-failure projection helper (`projectBulkFileSetResults`)
  potentially shared with M43's two-leg shape; R-NEW-58 ahead-of-feat
  trigger fires only if M43 likely consumes the same helper.

### M43 — Create-time file `--set` carve-out fold (D6 closure from v0.6-M38)

**Wire surface:** Two-leg dispatch — `create_item` (with placeholder
column_values for the file column) followed by
`add_file_to_column` (post-create file dispatch). Non-atomic by
construction; pre-flight Decision pins the atomicity-envelope shape
per cli-design §5.8.

**Empirical probe required at pre-flight:**

- Cleanup-on-failure probe — what happens to the created item if
  the post-create `add_file_to_column` leg fails? Does Monday
  GC the item, or does it leak? Drives the atomicity-envelope
  shape (rollback vs orphan-warn vs leave-as-is per cli-design
  §5.8).

**Open decisions at pre-flight:**

- **D1 — Atomicity envelope shape.** Three candidate shapes:
  (a) Best-effort rollback: failed file leg triggers a `delete_item`
      cleanup leg. Pre-flight Codex review will ask whether
      delete-after-create is safe (Monday's `delete_item` is
      destructive-permanent; agents have no recovery path if rollback
      itself fails).
  (b) Orphan-warn: failed file leg surfaces `internal_error` with
      `details.created_item_id` echo + `details.hint` pointing at
      the orphaned item (agents drive their own cleanup).
  (c) Leave-as-is: failed file leg surfaces `internal_error` with
      details but doesn't echo the orphan; relies on agents to
      diagnose via `monday item list`.
  Probe drives the cleanup-leg viability; if (a) is safe, default
  to (a); otherwise (b).
- **D2 — Dry-run envelope shape.** Mirrors v0.6-M38's `--dry-run`
  envelope verbatim plus a second `planned_changes` entry for the
  post-create file leg (`operation: 'add_file_to_column'` after
  `operation: 'create_item'`).
- **D3 — ERROR_CODES delta.** Likely zero. Atomicity failures route
  through `internal_error` with `details.reason:
  'create_then_file_upload_partial_failure'` discriminator.

**IMPL Codex review estimate:** 4-5 fix-up rounds (similar
profile to M42).

**R-class triggers anticipated:**

- Two-leg atomicity-envelope helper potentially shared across M11's
  `item move` cross-board, M43's create+file, and any future
  non-atomic mutation. R-NEW-58 ahead-of-feat trigger fires only if
  a 3rd consumer site is anticipated within v0.7 scope.
