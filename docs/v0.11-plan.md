## 2. Empirical probe basis

M54-G needed a probe before scoping. v0.11 candidate-selection
assumed read-side parity at `2026-01` but the 2026-05-22 dev-board
sweep had only confirmed `Item.description` shape at `2026-04`. If
the field were `2026-04`-only here, v0.11-G would re-couple to the
M39 SDK gate the candidate-selection explicitly broke.

**Probe ran 2026-05-23.** Script:
`scripts/probe/v0.11-item-description-2026-01.ts`; report:
`scripts/probe/v0.11-item-description-2026-01.report.txt`.
Invocation:
`DOTENV_CONFIG_PATH=.env.probe.local npx tsx scripts/probe/v0.11-item-description-2026-01.ts > scripts/probe/v0.11-item-description-2026-01.report.txt`.

Findings:

- ✅ `Item.description` IS present on the schema at `2026-01`
  (`kind=OBJECT name=ItemDescription`, no args). **No SDK gate.**
- ✅ `ItemDescription` shape: 2 fields — `id` (SCALAR/ID), `blocks`
  (LIST<DocumentBlock>). Same as `2026-04`.
- ✅ `DocumentBlock` shape: 9 fields at `2026-01` —
  `content` (**SCALAR/JSON, NOT `content_str` as the M40 probe
  prose implied**), `created_at` / `created_by` / `doc_id` /
  `id` (NON_NULL String) / `parent_block_id` / `position` /
  `type` / `updated_at`. The CLI projection picks 4: `id` /
  `type` / `content` / `position` (narrow surface, agent-useful
  body-shape).
- ✅ **Wire-nullable.** Classic-board item with no description
  returns literal `description: null`. The CLI normalises this to
  the sentinel `{id: null, blocks: []}` at the projection
  boundary so the table renderer + JSON consumers see a stable
  iterable shape.
- ✅ **Selection-set required.** Bare `description` without `{ ... }`
  rejects ("must have a selection of subfields"). Cassette
  `match_query: /description \{/` (with brace) is the right pin
  pattern.
- ⚠️ **Multi_level board reach blocked by token.** The probe token
  saw 2 boards, both `classic` — so the multi_level
  description-shape behaviour at `2026-01` was NOT directly
  verified. The 2026-05-22 dev-board sweep (`scripts/probe/m40-
  multilevel-discover.report.txt`) confirmed `description` works on
  multi_level boards at `2026-04` (returned populated
  `{id: 8781640, blocks: [...]}` for a top item on a multi_level
  board). Cross-API parity gives reasonable confidence the
  multi_level path works at `2026-01` too, but a future
  multi_level-scope probe is a watch-item (filed §22
  R-v0.11-NEW-1 below).

## 3. Per-milestone decisions

> Land at each milestone's pre-flight contract diff. M54-G
> dimensions: (D1) shape — narrow verb vs extend
> `ITEM_FIELDS_FRAGMENT` vs both; (D2) wire selection-pin guard

### M54-G — `Item.description` read-side (pre-flight CLOSED 2026-05-23, `<pre-flight-sha>`)

**Probe basis:** §2 above. `Item.description` confirmed at API
`2026-01` (the CLI pin) — no SDK gate, ships standalone.

**Headline finding (drove the verb-vs-fragment shape).** The
`DocumentBlock.content` field is a JSON scalar carrying the doc
block's body payload (the shape varies by block `type` per
Monday's doc-content model). With `ITEM_FIELDS_FRAGMENT` already
serving ~16 consumers — every item read + every item-returning
mutation — extending it universally would have items in `item
list`'s N-row collections all carrying their block-JSON payload by
default. That's heavy bloat for a field most items don't populate
and most reads don't need.

- **D1 — Shape: NARROW VERB.** `monday item get-description <iid>`
  ships as a dedicated read verb mirroring v0.9-M52's `board views
  <bid>` carve-out. ITEM_FIELDS_FRAGMENT untouched; 0 fixture ripples;
  0 existing call sites modified. Trade-offs:
  - **(b) Narrow verb (chosen).** Heavy/nested content stays
    opt-in. Verb-local schema (`src/api/item-description.ts`) +
    verb body (`src/commands/item/get-description.ts`). +1 command
    (118 → 119). Mirrors the M52 precedent literally — but unlike
    M52 (which extended a HEAVY single-sourced schema
    `boardMetadataSchema` AND added a narrow verb), there's no
    "heavy item schema" to extend for items; `ITEM_FIELDS_FRAGMENT`
    IS the lightweight shared projection across 16 consumers. The
    M52 "both" pattern doesn't translate cleanly — extending the
    fragment plus adding the verb would double the blast radius
    without commensurate benefit.
  - **(a) Extend `ITEM_FIELDS_FRAGMENT`.** Universal projection,
    every item read carries `description`. ~16 consumer files
    touched (no body change, but query bodies grow); ~33+ existing
    item fixtures across `tests/integration/commands/**` need
    `description: null` added; M15-style canonical-Item-shape
    invariant widened across all consumers; `item list` returning
    100 items × each block-list-JSON payload = significant wire
    bloat for the dominant read pattern. Per `.claude/rules/
    workflow.md` "Read-side field-add" (graduated v0.9-M52):
    heavy/nested fields with selective utility → narrow verb. The
    rule's spirit clearly favours (b) for this shape.
  - **(c) Both.** Faithful to M52's precedent in form but not
    spirit — M52 extended boardMetadataSchema (1 consumer:
    `board describe`) + added `board views`. For items the analog
    would extend ITEM_FIELDS_FRAGMENT (16 consumers) + add the
    verb. The "lightweight + universally-useful" criterion for the
    shared-schema choice FAILS for `Item.description` (it's
    neither lightweight nor universally populated). Defer to the
    narrow verb alone.

  **User AskUserQuestion 2026-05-23** confirmed (b). Single
  round-trip; recommendation (b) with preview accepted without
  modification.

- **D2 — Wire selection-pin guard: BOTH LAYERS** (per the v0.9-M52-
  graduated rule in `.claude/rules/testing.md` "Wire selection-pin
  for raw-GraphQL SDK-drift fields"). Not really a binding decision
  — the rule mandates both layers for any SDK-drift-class raw-
  GraphQL selection. Implementations at pre-flight:
  - **Cassette layer.** `tests/integration/commands/item-get-
    description.test.ts` happy-path interaction asserts
    `match_query: /description \{/` (with brace — confirmed by
    probe: bare `description` without selection-set rejects). A
    refactor dropping `description { ... }` from
    `ITEM_DESCRIPTION_QUERY` fails this assertion in CI before
    reaching live API.
  - **Live-smoke layer.** `tests/e2e/live-schema-drift.test.ts`
    new `it('ITEM_DESCRIPTION_QUERY ...')` block runs the EXACT
    production document against the live API + asserts
    `toHaveProperty('description')` on the response item. A
    Monday-side removal of `Item.description` surfaces here even
    if the document still validates as a syntactically-correct
    GraphQL query.
  - **3rd consumer of R-v0.9-NEW-6** (the graduated rule). M51
    (`hierarchy_type`) was the 1st; M52 (`views`) was the 2nd;
    M54-G (`description`) is the 3rd. Pattern continues to hold
    across raw-GraphQL SDK-drift consumers.

- **D3 — `description: null` normalisation: NORMALISE TO SENTINEL.**
  Probe confirmed Monday returns literal `description: null` for
  items with no description set. The CLI normalises this to
  `{id: null, blocks: []}` at the `parseItemDescription` boundary
  before emit. Trade-offs:
  - **Normalise (chosen).** Single-resource envelope's `data` is
    always an iterable object — the table renderer
    (`src/utils/output/table.ts` `renderSingle`) iterates
    `Object.keys(data)`, so a literal `null` would crash it.
    Agents distinguish absent (`data.id === null`) from present
    (`data.id !== null`); blocks-empty case (`data.id !== null &&
    data.blocks.length === 0` — created then emptied) stays
    distinguishable.
  - **Surface bare null.** Wire-faithful but breaks the table
    renderer + costs every agent a null-check before destructuring.
    Out-of-scope refactor needed.
  - **Add an explicit `state: 'absent' | 'present'` discriminator.**
    Heavier schema surface for no agent ergonomics gain (the same
    bit is encoded in `id === null`).

- **D4 — `DocumentBlock` field projection: NARROW 4-FIELD.** Surface
  `id` / `type` / `content` / `position` out of the 9 wire fields.
  Dropped (kept available for future widening): `parent_block_id` /
  `doc_id` / `created_at` / `created_by` / `updated_at`. Rationale:
  the body-shape use case needs `id` (stable referencing), `type`
  (block-kind discriminator), `content` (the body payload), and
  `position` (ordering); the 5 metadata fields belong on a `doc get`-
  tier verb (M32 already surfaces them on `doc get`'s
  `DocumentBlock` projection). Future widening costs nothing —
  adding fields to a projection is non-breaking per `cli-design.md`
  §6.1.

- **D5 — ERROR_CODES delta: ZERO.** Registry stays at 29. The new
  verb routes failures through existing codes:
  - `not_found` — Monday returns no item row (item id missing).
  - `usage_error` — non-numeric / shape-invalid item id at argv
    parse boundary.
  - `unauthorized` — HTTP 401 (existing transport handler).
  - `internal_error` (`details.issues`) — shape regression in
    Monday's `ItemDescription` payload (`parseItemDescription`
    R18 parse-boundary wrap).

  118 → **119 commands** (+1 for the new verb).

**Codex pre-flight review R1 CONVERGED** (0 P1; 1 P2 + 1 P3 both
applied inline at this same pre-flight commit). Findings:

- **P2-1 (W8) — Malformed `items[0]` rows emitted as "no
  description" sentinel.** Without the guard, the verb body's
  `isPlainObject(first) ? first.description : null` pattern
  collapsed a non-object scalar row (e.g., `items: [42]`) to
  `descriptionRaw = null`, which `parseItemDescription` then
  normalised to the wire-null sentinel. Indistinguishable from
  "no description set." **Fix:** added explicit
  `if (!isPlainObject(first))` throw of `internal_error` with
  `details.reason: 'malformed_item_row'` + `details.item_id` BEFORE
  the description pluck (`src/commands/item/get-description.ts` —
  the Codex-pointed line). New integration test pins the
  shape-failure surface (`items: [42]` → exit 2 + `internal_error`
  + `details.reason: 'malformed_item_row'`).
- **P3-1 (W5) — Unit-test selection-pin too loose to catch
  `blocks { id ... }` selection drop.** The pre-fix assertion
  `toMatch(/\bid\b/)` was satisfied by `$ids`, the item-row `id`,
  OR the description `id` — a refactor dropping `blocks { id type
  content position }` from the document would still pass. The
  cassette `match_query: /description \{/` doesn't catch this
  either (it pins the `description {` block but not the nested
  `blocks { ... }` selection). **Fix:** tightened the regex to
  `/blocks\s*\{[^}]*\bid\b[^}]*\btype\b[^}]*\bcontent\b[^}]*\bposition\b/s`
  — scopes the 4-field assertion INSIDE the `blocks { ... }`
  block. A refactor dropping any of the 4 named subfields now
  fails the unit test before reaching CI.
