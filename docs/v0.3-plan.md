# v0.3 implementation plan

> **Status:** plan, not contract. The binding contract is
> [`cli-design.md`](./cli-design.md). This document sequences the
> work needed to ship v0.3 of that contract; it doesn't redefine it.
> If a conflict arises, `cli-design.md` wins and this plan is updated.

## 1. Scope summary

v0.3 is "**Monday Dev + multi-profile** — agents bring their own
identity, narrate their work against sprint/epic/release/task
artefacts, and stop iterating boards by hand to find the things
they own." v0.2 gave agents the full mutating CRUD surface (item
lifecycle, board structure, comment threads); v0.3 layers four
distinct surfaces on top: (1) the slipped tentative-row writer
expansion (`tags` / `board_relation` / `dependency`) plus the
verb-shaped `time_tracking` extension that closes the
column-type roadmap for v0.3-target slots, (2) multi-profile
credentials cache (`monday auth login` + `~/.monday-cli/config.toml`)
plus the diagnostics cluster (`monday status` + `monday usage`)
that probes its state, (3) the cross-board read upgrades
(cross-board `item search`, `board favorites`, `item history`,
`item update --continue-on-error`) that lift the v0.1 single-board
read assumption, and (4) the `monday dev` namespace + outbound
write surface (notifications, webhooks). v0.3 is the first version
where an agent can fully self-onboard: log in, probe its
configuration, discover what's available, plan against a sprint,
and narrate progress without ever touching a Monday UI tab.

**In scope (from `cli-design.md` §13 v0.3 + §5.3 writer-expansion
roadmap):**

| Group | Commands |
|-------|----------|
| **column writers (slipped from v0.2)** | Friendly translators for `tags`, `board_relation`, `dependency` (the v0.2 tentative row that didn't converge in v0.2's window). `--set-raw` accepts these today; M19 lifts them into the friendly translator. |

**Universal partial-success rule (cli-design §6.1 compliant — same
shape as v0.2).** Multi-target verbs in v0.3 (M25 `item update
--continue-on-error` is the only v0.3 consumer; M27 `notification
send` stays single-recipient per cli-design §4.3) emit one
**success envelope** (`ok: true`) with per-target results in
`data.results: [...]`. Each record carries its own
`{<target_id_field>, ok: true | false, error?}`. The shared
envelope-builder (`buildPartialSuccessMutation`, lifted in v0.2)
takes the field name as a parameter. The envelope's top-level
`error` slot is reserved for whole-call failure; all-failed-but-
each-call-attempted is still `ok: true` and the agent reads
`data.results` to determine outcomes. v0.3 introduces no contract
revision to §6.1.

**Out of scope (deferred per `cli-design.md` §13 "Explicitly
deferred from v0.1's stable contract"):**

- `item watch <iid>` (v0.4 — polling cadence question still open
  per cli-design §14.4).
- Bulk operations with `--concurrency` (v0.4 — probed against
  Monday's per-account concurrency cap).
- Asset upload (`add_file_to_column`, `add_file_to_update`) — the
  `files`-shaped column write path (v0.4).
- Shell completion (bash / zsh / fish) via commander (v0.4).
- `doc list/get` (v0.4 read-only; full docs CRUD deferred further).
- `team` create/manage (v0.4).
- Boolean filter DSL — v0.3 keeps the v0.1 / v0.2 `--where`
  operator allowlist + `--filter-json`. Pencilled at v0.3 stretch
  / v0.4 firm; only ships when fixture-driven adoption metrics
  show concrete demand.
- `monday item recreate-from-archive` — still no misleading
  `restore` command (cli-design §5.4 stands as a permanent
  non-goal-adjacent decision).

**Permanent non-goals (per cli-design §13 — reminded here so plan
readers don't propose them as v0.3 candidates):**

- Hosting webhooks (CLIs can't expose public HTTP — out of model);
  v0.3's `webhook create` is the *registration* shape against
  Monday, not a receive endpoint.
- App framework / installable monday apps (different surface
  area).
- Real-time GraphQL subscriptions (Monday's endpoint doesn't
  support them).
- Telemetry, update-notifier, analytics — ever.
- Forms (Monday's public-submission feature) — same hosted-
  endpoint shape as webhooks.
- Saved queries / aliases — would silently change behavior across
  machines; shell aliases / shell functions are the established
  UNIX answer.
- `monday undo` (replay-based reversal of recent mutations) —
  Monday's state model is authoritative and concurrent; honest
  substitutes are `--dry-run` (v0.1) and `item history` (v0.3 —
  M24 below).

What's **missing** that v0.3 needs (each filled by the named
milestone):

- An **account-tag directory** module (M19) mirroring the
  `userByEmail` user-directory pattern in `src/api/resolvers.ts`
  (M5a — there is no standalone `user-directory.ts` module; the
  user-directory cache / lookup / refresh-on-miss machinery lives
  inside `resolvers.ts` lines 192–402). Monday's tags are account-
  scoped (`account_tags` returns the directory; `tags` column
  values reference tag IDs). The friendly translator needs to
  resolve `<tag1>,<tag2>` to tag IDs at boundary; misses surface
  the `tag_not_found` error code (registered pre-M19 at `4c652d5`
  per §8 decision 1).
- A **linked-board enumeration + complexity-budget** path (M19)
  for `board_relation` and `dependency`. Monday's wire shape is
  `{ item_ids: [N1, N2] }` referencing items in the column's
  `settings.boardIds ?? [settings.boardId]`. The friendly
  translator validates input items belong to those allowed
  boards before constructing the wire payload — a per-call
  Monday lookup with complexity-budget interaction (see §6
  risk register).
- A **multi-profile config loader** (M21) — v0.1/v0.2 read
  `MONDAY_API_TOKEN` from env or `.env`. v0.3 adds
  `~/.monday-cli/config.toml` with `[profiles.<name>]` blocks +
  `--profile <name>` global flag. **Selection order is fixed by
  cli-design §7.2:** `--profile` flag > `MONDAY_PROFILE` env >
  `default_profile` in config > `MONDAY_API_TOKEN` env (falls
  back to v1 mode if no config file exists). **Tokens are never
  stored in the config file** — profile entries reference an env
  var name via `api_token_env = "MONDAY_API_TOKEN_<NAME>"` per
  cli-design §7.2.
- A **credentials cache primitive** (M21) —
  `~/.monday-cli/credentials` (mode `0600`) for `monday auth
  login`'s OAuth flow result per cli-design §7.3. Format
  question is open (cli-design §14.5); default leans toward our
  own JSON.
- A **self-test harness** (M22) for the diagnostics cluster —
  mockable transport seam for `monday status`'s probes (so
  status itself is testable without real network), plus a
  rolling-24h-budget query path for `monday usage`.
- A **per-item event projection layer** (M24) — `item history`
  surfaces Monday's `activity_logs` entries as event objects with
  `created_at`, `actor_id`, `kind`, `before` / `after`. Distinct
  from existing item / update projections; a new §6 envelope
  shape (cli-design §13 v0.3 entry).
- A **workflow-shortcut layer** (M26) over the v0.1/v0.2
  CRUD surface — `dev sprint`, `dev epic`, `dev release`,
  `dev task` are convention-driven helpers (per cli-design
  §2.7 — Monday Dev is convention, not API). They translate
  workflow vocabulary to standard board / item operations.
- An **outbound notification + webhook surface** (M27) —
  `notification send` (Monday's `create_notification` mutation;
  per-user-id targeting), `webhook list/create/delete`
  (`webhooks` query + `create_webhook` / `delete_webhook`
  mutations). New nouns. **Webhooks are live-only for v0.3** —
  not part of cli-design §8's cache scope (boards / users /
  schema only). If webhook caching becomes load-bearing later,
  it lands as a v0.3.x or v0.4 §8 contract-extension PR.
- A **multi-level subitem creation** path (M28) — Monday allows
  `create_subitem` with a parent that is itself a subitem; the
  current friendly translator caps at single-level. Shipping
  multi-level requires hierarchy validation (depth limit per
  Monday's policy — typically 3 levels).

## 3. Milestone sequencing

Ten milestones (M19–M28). Each milestone is a coherent commit
cluster (3–10 commits) ending on a green tree with the listed
exit criteria met. Earlier milestones unblock later ones; do not
start M(N) until M(N-1)'s exit criteria are satisfied. Each
milestone updates `docs/output-shapes.md` for any new command
shapes it lands and adds envelope snapshots for any new emitted
shape.

Order at a glance: **writer-expansion close → time_tracking →
auth foundations → diagnostics → cross-board reads → history →
partial-success bulk → dev namespace → outbound writes → subitem
expansion + release prep**.

```
       M19                                — writer expansion close (slipped tentative row)
       M20                                — time_tracking start/stop verbs
       M21 ─ M22                          — auth foundations (login + profiles) → diagnostics (status + usage)
       M23 ─ M24 ─ M25                    — cross-board reads (search + favorites) → history → partial-success bulk
       M26                                — dev namespace (workflow shortcuts)
       M27                                — outbound writes (notifications + webhooks)
       M28                                — subitem expansion + polish + 0.3.0 release prep
```

**Pre-flight design clearance** (must close before any feat
commit lands; mirrors M16's seven-round pre-flight cadence
that pinned 22 contract bugs before code shipped):

1. **`tags` translator shape.** Input form: `<tag1>,<tag2>`
   (comma-split, trimmed). Output wire shape:
   `{ tag_ids: [N1, N2] }`. Resolution: per-account tag
   directory lookup. New `src/api/tag-directory.ts`
   module mirrors the `userByEmail` user-directory
   pattern in `src/api/resolvers.ts` (M5a precedent —
   account-scoped lookup, cache-aware via §8
   invalidation, exposes
   `resolveTags({ client, input, env?, noCache? }):
   Promise<{ ids, misses, source }>` and
   `loadAccountTags({ client, env?, noCache? }):
   Promise<{ tags, source, cacheAgeSeconds }>` — the
   M19 pre-flight contract diff at `d822982` pinned
   the surface as object-form inputs with a required
   `MondayClient`, mirroring `UserByEmailInputs`
   verbatim). Cache key shape:
   `{ kind: 'account-tags' }` (single-account scope; no
   per-board fan-out). Misses surface as a single
   `tag_not_found` error code with `details: { tags:
   <misses[]>, hint: 'Run \`monday account tags\` to
   list available tags.' }` — array shape per §8
   Decision 1 (multi-miss `--set tags=foo,bar,baz`
   surfaces all missing tags in one envelope, NOT one
   error per miss). The hint hard-pins `monday account
   tags` as a v0.3 read-verb deliverable per the
   §6.5 PR's forward-looking commitment (cli-design.md
   §6.5 entry landed at `4c652d5`).
2. **`board_relation` translator shape.** Input form:
   `<iid1>,<iid2>` (comma-split item IDs). Output wire
   shape: `{ item_ids: [N1, N2] }`. Resolution: per-board
   `column.settings.boardIds ?? [column.settings.boardId]`
   list (already in board metadata via M3); validate that
   each input item ID belongs to one of those allowed
   boards. Mismatched item IDs surface as
   `usage_error` with `details: { item_id: <id>,
   allowed_boards: [...], hint: 'item belongs to board X
   but column accepts only [...]' }`. **Complexity-budget
   interaction:** validating each input item via
   `items(ids: [N])` query would burn complexity per item;
   batch via `items(ids: [N1, N2, ...])` to amortise.
   Decision: batch with a hard cap of 25 items per
   `--set` call (matching Monday's documented
   relation-column item cap); >25 surfaces `usage_error`
   pre-network.
3. **`dependency` translator shape.** Identical wire shape
   to `board_relation` (`{ item_ids: [N1, N2] }`); the
   distinction is that Monday's `dependency` column has
   its own settings and its own per-call quirks. Validate
   against `column.settings.dependencyBoards ?? [...]`
   (Monday's separate `dependency` settings field).
   Otherwise treat as a sibling of `board_relation` —
   same resolution path, same complexity-budget
   interaction, same per-call cap.
4. **Clear payloads** (cli-design §5.3 clear table). All
   three types clear to `{}` via `change_column_value`
   (matching v0.2's expansion of the per-type clear
   table; see cli-design §5.3 "Clearing column values").
   Bulk `item clear --where ... <col>` (already shipped
   in M12) inherits this on day one.
5. **Dry-run shape.** Per cli-design §5.3 dry-run example
   block (lines 2416–2434) — `data: null`,
   `meta.dry_run: true`, `planned_changes: [...]` array.
   Each tentative-row type emits `resolved_ids` (column
   ID resolution) + `diff` (`{from: previous, to: new}`)
   + `details` (resolution-source hint: tag-directory
   match for `tags`; allowed-boards-validated for
   `board_relation` / `dependency`).
6. **`example_set` per writable column** (cli-design §3.2
   `board describe`). All three new types need
   `example_set` strings — `"tag1,tag2"` for `tags`,
   `"<iid1>,<iid2>"` for `board_relation` /
   `dependency`. Update `commands/board/describe.ts`
   `example_set` builder to cover the new types so
   `board describe` is self-sufficient for agents
   constructing M19-class `--set` calls.

**Decisions closed at M20 pre-flight (this commit):**

- **Decision 4.1 — `start` against a running column:**
  Closed: `usage_error` (reuses the existing code rather

### M24 — `item history <iid>`

**New §6 envelope shape.** Per-item activity log surfaces
**status changes, column edits, assignments, AND comments
interleaved chronologically** (per cli-design §13 v0.3
entry — the comments-interleaved requirement is part of
the contract surface). Two source streams merge in the
projector: Monday's `activity_logs` (status / column /
assignment events) + Monday's `updates` (comment thread).
Output event objects carry `created_at`, `actor_id`,
`kind`, `before` / `after`; the `kind` taxonomy includes
an `update_posted` (or similar) variant for comment
events alongside the activity-log kinds. Distinct from
existing item / update projections (item = current state;
update = comment thread; history = chronological merged
event log).

**Scope size:** M–L (one new noun-verb shape; new
two-source merge projection layer; per-source pagination
both consumed; per-event ordering by `created_at`).

**Decisions to close before kickoff:**
- **Pagination shape.** Page-numbered (Monday's native
  for `activity_logs`) vs cursor-style. Recommended:
  page-numbered surfaced via `--page <n> --limit <n>`
  for activity-log slice; updates pagination uses the
  v0.1 update-list cursor walker. The merge projection
  walks both sources to a unified time horizon per
  page.
- **Merge semantics.** Recommended: drain both sources
  to a wall-clock cap (`--since <iso>` / `--until
  <iso>`) and emit merged events ordered by
  `created_at`. Stream output preserves order across
  the merge.
- **`before` / `after` shape.** Monday's `activity_logs`
  entries have a `data` field that's a JSON string. The
  projector parses it and surfaces typed before/after
  pairs per `kind`; unknown kinds surface as raw `data`
  with a warning. The kind taxonomy is a fresh contract
  surface (cli-design §6 needs an extension entry — see
  §8 decision 2). Comment-event `before` / `after` is
  always `null` (comments are append-only events; the
  body lives in the event payload).
- **Streaming.** Reuse `startNdjsonStream` (R52) for
  large per-item histories. Trailer meta carries
  `total_pages` for the activity-log slice and
  `next_cursor` for the updates slice (both surfaced
  per cli-design §6).

item-history-projection.ts`, `src/commands/item/
history.ts`. Output-shapes.md gets a new top-level entry
for the event-object shape.

## 4. Cross-cutting "definition of done" per command

Every v0.3 command, regardless of milestone, satisfies the
following before its containing milestone closes:

- **One file per subcommand** in `src/commands/...`,
  exported as `CommandModule`, registered in
  `cli/index.ts`.
- **zod schema for argv at the boundary** — never trust
  commander's runtime shape (per `.claude/rules/cli.md`
  "Commander's runtime option shape" trap). All flags
  parse through `globalFlagsRawSchema` + per-command
  schema; commander's coerced types (string for `<n>`,
  string for `<list>`) get coerced/split inside the
  schema, never inside the command body.
- **One Monday GraphQL operation per file** — top-of-
  file comment names the operation(s) the command calls;
  agents grep for this when planning changes.
- **Universal envelope on every success and failure
  path.** Success: `{ok: true, data, meta, warnings}`.
  Failure: `{ok: false, error: {code, message, http_
  status, monday_code, request_id, retryable, retry_
  after_seconds}, meta}`. Agents key off `error.code`,
  never English.
- **Stable error code from the §6.5 registry.** v0.3 may
  extend the registry (M19's `tag_not_found`; M24's
  history-event-kind taxonomy if it lands as new error
  codes). Each extension lands as a separate pre-
  milestone contract-change PR with its own Codex review
  per CLAUDE.md workflow.
- **NO interactive prompts.** Destructive ops without
  `--yes` return `confirmation_required`. M19's
  tentative-row writers inherit this from M5b. M27's
  webhook deletes are destructive — `--yes` required.
- **Exit codes per §7 standard:** 0 success / 1 usage or
  `confirmation_required` / 2 API or network / 3 config
  / 130 SIGINT.
- **Dry-run support** for any destructive or high-impact
  verb. M19's tentative-row writers ship dry-run from
  day one; M25's partial-success bulk ships
  `--dry-run` (per-item planned-changes preview).
- **Cache invalidation eager + correct.** Mutations
  follow cli-design §8. M27's webhook lifecycle is
  live-only — outside §8's cache scope and does not
  extend the §8 contract.
- **Stdin support** for any "operate on this thing" verb
  per cli-design §10.1. M19's tentative-row writers
  inherit the stdin convention from M5b.
- **NDJSON streaming** for any verb with unbounded
  collection output. M23 cross-board search + M24
  history are the v0.3 streaming consumers.
- **`example_set` per writable column** (M19 only).
  `monday board describe` self-sufficient for agents
  constructing M19-class `--set` calls.
- **Tests cover every branch.** Coverage floor 95 / 95.45
  / 95 / 95 (statements / branches / functions / lines)
  per `vitest.config.ts`. M19's focused coverage push
  should target ≥95.5% branches.
- **Envelope snapshots** for every emitted shape (success
  + failure variants).
- **`docs/output-shapes.md`** ToC entry for every new
  command shape.
- **`docs/cli-design.md`** updates for any binding
  decisions (separate pre-milestone PR with Codex
  review).
- **Codex pre-flight review** before first feat commit;
  Codex implementation review before milestone close.

## 5. Testing strategy — the pyramid, made explicit

v0.3 inherits v0.2's pyramid (unit / integration / E2E).
New cassette categories v0.3 introduces:

- **Account-tag directory cassettes** (M19) — `account_
  tags` query responses (happy / empty / many tags /
  paginated). Mirrors `users(...)` cassettes from M5a.
- **Board-relation allowed-boards validation cassettes**
  (M19) — `items(ids: [...])` batch-lookup responses
  with each item's `board_id` field.
- **OAuth-flow + credentials cache fixtures** (M21) —
  full OAuth dance per cli-design §7.3 (browser-open
  intent, localhost callback listener, code exchange,
  credentials write to `~/.monday-cli/credentials` mode
  `0600`). Mock OAuth seam injected via
  `__test_oauth_helper` env var per cli-design §7.3.4 —
  the helper bypasses ONLY the browser-open + listener
  steps (synthesising a redirect with the CLI's own
  generated `state` + the fixture's `code`); the token
  exchange itself still hits the network boundary so
  `FixtureTransport` cassettes drive the
  `/oauth2/token` response shape (success + 4xx variants
  for `oauth_failed.reason: "code_exchange_failed"`).
  Three `force_*` fixture flags exercise the local-side
  failure branches without going through the network:
  `force_csrf_mismatch`, `force_user_denied`,
  `force_listener_timeout`. Cache file mode `0600`
  verified via `fs.fstat`-against-open-descriptor in the
  test.
- **Multi-profile config fixtures** (M21) — tmp-dir
  `~/.monday-cli/config.toml` with N profiles, each
  switching transport seam to its own fixture cassette.
- **Probe transport fixtures** (M22) — DNS / TCP / TLS
  / 401 each with happy + failure variants. Mock
  transport seam runs probes without real network.
- **Complexity-budget fixtures** (M22) — `account.
  complexity` + `webhooks.complexity` responses with
  near-budget + over-budget variants.
- **Cross-board fan-out cassettes** (M23) — N-board
  fan-out via fixture transport; per-board complexity
  budget.
- **Item history cassettes** (M24) — TWO-source merge
  coverage per cli-design §13 v0.3 ("activity log
  + comments interleaved chronologically"):
  `activity_logs(item_id)` responses with each
  documented `kind` covered; `updates(item_id)` comment-
  thread responses; unknown-kind fallback path; merge-
  order cases where activity events and comment events
  interleave by `created_at` (assert chronological
  emission order across the merge); pagination
  exhaustion on both sources to a unified time horizon.
- **Webhook cassettes** (M27) — `webhooks(board_id)`
  query, `create_webhook` mutation, `delete_webhook`
  mutation. Event-type enum pinned at parse boundary.

**Adversarial test discipline carries over from M0/M2:**
every redaction-affected output path (M21's credentials
cache, M22's `monday status` env-var pickup summary)
must assert that the literal token is absent from every
emitted byte across the suite. The token-leak detection
suite extends with M21's credentials-cache scrubbing.

## 6. Risk register

Known design risks for v0.3, by milestone:

- **M19 `tags` translator — account-tag directory cache
  invalidation.** Tags can be created / deleted via
  Monday's UI between CLI invocations. Stale cache could
  surface `tag_not_found` for a tag that's been re-
  created with a different ID, OR map to a deleted tag's
  ID and produce a wire-shape mismatch. Mitigation:
  conservative TTL (5 min cache lifetime via §8 leg-
  count split), `--refresh-tags` flag for force-refresh,
  surfaced cache-age in `meta.cache_age_seconds`.
- **M19 `board_relation` / `dependency` — complexity-
  budget interaction.** Per-call validation of N input
  items burns complexity. Mitigation: hard cap at 25
  items per `--set` call; documented in cli-design §5.3.
- **M21 OAuth flow — secret in transit.** OAuth dance
  passes a code through HTTP redirects. Mitigation:
  full OAuth dance per cli-design §7.3 ships with a
  randomised localhost callback port + state-parameter
  CSRF check (`crypto.timingSafeEqual` with explicit
  length-check guard so length-mismatched buffers route
  to `oauth_failed.reason: "csrf_mismatch"` rather than
  `internal_error`) + short-lived code (Monday's docs
  describe roughly 10-minute validity at the time of
  writing; **probe-time confirmation** at M21 pre-flight
  pins the exact TTL per §22 R-watch-item); the callback
  listener binds to `127.0.0.1` only (never `0.0.0.0`)
  and validates the `state` parameter before any code
  exchange. If the dance proves out of session-budget,
  paste-in is a separate cli-design §7.3 amendment PR
  before M21 first feat commit, NOT a silent
  implementation choice.
- **M21 credentials-cache scrubbing.** New file path
  (`~/.monday-cli/credentials`) needs to be scrubbed
  from any debug / status / config-show output.
  Mitigation: extend `redact()` to recognise the
  credentials path; redaction self-test (M22's `monday
  status`) asserts the scrubbing.
- **M22 `monday status` — false negatives.** Probe at
  one moment may say "everything works" while a
  transient issue resolves between probe and real call.
  Mitigation: surface probe timestamp in output; agents
  retry on transient.
- **M22 `monday usage` — Monday's complexity surface
  drift.** If Monday extends the complexity surface
  (per-minute, concurrency-cap), `monday usage`'s
  envelope needs to grow without breaking. Mitigation:
  envelope is additive-only; new fields land as v0.3.x
  minor bumps.
- **M23 cross-board fan-out — pagination consistency.**
  Item state can change during a multi-board walk.
  Mitigation: surface `meta.snapshot_drift: true`
  warning if any per-board cursor returns `stale_cursor`
  mid-walk.
- **M24 history — `kind` taxonomy drift.** Monday adds
  new `activity_logs.kind` values over time. Mitigation:
  unknown-kind fallback path surfaces raw `data` with a
  warning; cli-design §6 envelope additive-only.
- **M27 webhook events — endpoint validation.** Monday
  validates webhook URLs server-side. Mitigation:
  surface Monday's wire `validation_failed` mapped to
  `usage_error`; document the required URL shape (HTTPS
  + reachable from Monday's IPs).
- **M28 multi-level subitem hierarchy — depth limit
  drift.** Monday's documented 3-level limit could
  change. Mitigation: validate against documented limit
  at parse boundary; surface Monday's wire validation
  error if Monday's actual limit shifts.

```ts

/* c8 ignore start — stub body rejects on every path. */

  _inputs: FooBarInputs,
): Promise<FooBarResult> =>
  Promise.reject(
    new ApiError(
      'internal_error',
      'fooBar is a v0.3-M<X> pre-flight stub — ...',
      { details: { hint: NOT_IMPLEMENTED_HINT } },
    ),
  );
/* c8 ignore stop */
```

### R-watch-item — `FixtureTransport` order-tolerance for parallel transport calls

Surfaced by the Node 24 cassette-ordering flake fix
(`7dbcf7e fix(m11): serialise cross-board metadata
loads`). `runCrossBoardMove` loaded source + target
board metadata via `Promise.all`; the test
`FixtureTransport` (`tests/fixtures/load.ts`)
**strictly consumes `queue[0]` per request**, and on
Node 24 microtask scheduling occasionally flips the
order in which two concurrent transport calls reach
the cassette. When target arrives before source,
queue[0]'s `match_variables: {ids: ['111']}` fails
the variables check, the transport throws
`cassette mismatch`, and the runner maps the
`internal_error` envelope onto exit code 2 — turning
an order-correct cassette into a flake.

**Single consumer fix shipped at `7dbcf7e`** —
serialise the two metadata loads in `move.ts`.
Production-latency cost is ≤one cache-miss network
roundtrip (~300ms vs max-of-two); negligible for an
interactive mutation. The alternative durable fix
(out-of-order matching in `FixtureTransport` when
`match_variables` disambiguate the queue entry) would
weaken cassette-as-strict-sequence semantics across
105 test files for the benefit of one `Promise.all`
call site — the narrower fix wins.

**Trigger.** Watch-item, not a scheduled lift. Fires
if any of:
- A second `Promise.all` call site lands in `src/` and
  cannot be cleanly serialised (e.g., genuinely
  independent walkers with no causal ordering and
  measurable wall-clock benefit).
- A 3-consumer trigger fires across `Promise.all` /
  `Promise.race` / parallel-walker shapes (e.g., M23
  cross-board search fan-out across favorites, M27
  webhook batching).
- Test-flake retrospectives surface a second
  cassette-ordering case that can't be fixed by
  serialising the production code.

**Risk:** medium if it fires — the FixtureTransport
hardening would touch the cassette-matching algorithm,
which 105 test files depend on for strict-ordering
detection power. Findings that previously surfaced
as `cassette mismatch` (a real test-detection signal
when production sends operations out of expected
order) would silently succeed under out-of-order
matching. Mitigation if scheduled: gate the new
behaviour behind an explicit `match_variables` slot
(strict ordering preserved when match_variables is
omitted; out-of-order matching ONLY when
match_variables disambiguates).

**When to schedule:** **deferred — watch only.** No
action this session. Re-evaluate at any future
milestone that introduces a second Promise.all call
site or a 3rd parallel-walker shape.
