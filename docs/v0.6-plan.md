# v0.6 implementation plan

> **Status:** plan, not contract. The binding contract is
> [`cli-design.md`](./cli-design.md). This document sequences the
> work needed to ship v0.6 of that contract; it doesn't redefine it.
> If a conflict arises, `cli-design.md` wins and this plan is updated.

## 1. Scope summary

v0.6 is "**fill the column-write story**" — agents reach the last
column-type-shape Monday exposes (file-shaped columns) through the
same friendly `--set <col>=<val>` surface they already use for every
other writable column-type. v0.5 closed the team-writers + workdocs
CRUD mutation backlogs. v0.6 picks up the longest-running carry-over
in the §13 backlog: the files-shaped friendly `--set` translator that
slipped from v0.4 → v0.5 → v0.6 across two consecutive release-preps
because neither cycle picked up the translator-to-multipart-wire
dispatch.

**In scope (from `cli-design.md` §13 v0.6 + Appendix B verb-noun
matrix):**

| Group | Commands |
|-------|----------|
| **files-shaped `--set`** | `monday item set <iid> <file-col>=<path>` + `monday item update <iid> --set <file-col>=<path>` — friendly translator extension dispatching from the standard `--set` boundary into v0.4-M31's multipart wire (`add_file_to_column`) rather than the JSON `change_column_value` path the other writable types use. No new wire fetcher (reuses M31's `addFileToColumn` verbatim); no new transport seam (multipart shipped at v0.4-M31); no new ERROR_CODE (29 stays). |
| **polish** | Refreshed envelope-snapshot suite for v0.6 surfaces; `output-shapes.md` ToC audit; README quickstart updates; CHANGELOG `0.6.0` entry; version bump. |

**Universal partial-success rule** (cli-design §6.1 compliant — same
shape as v0.2 / v0.3 / v0.4 / v0.5). M38 ships single-item only —
bulk `item update --where ... --set <file-col>=<path>` REJECTS at
the column-resolution boundary per D5 closure (parse-time can't
know — column types only resolve after metadata loads; defers to
v0.6.x for the per-item file-set partial-success envelope). v0.6
introduces no contract revision to §6.1.

**Out of scope (deferred per `cli-design.md` §13 + carried over from
v0.5 deferrals):**

- Bulk `item update --where ... --set <file-col>=<path>` — defers to
  v0.6.x candidate-selection. Per-item file dispatch + partial-success
  envelope + `--concurrency` interaction each carry design dimensions
  (per-item retry timing for multipart; per-item asset slot in
  envelope; concurrent multipart with shared transport) that warrant
  their own milestone cluster.
- `item create --board <bid> --name <n> --set <file-col>=<path>` —
  REJECTS at column-resolution boundary per D6 closure. Create-time
  file upload would need: (a) `create_item` with placeholder
  `column_values`, (b) post-create `add_file_to_column` — non-atomic,
  opens state-safety holes per cli-design §5.8 "atomicity, state
  safety, and idempotency". Defers to v0.6.x once a clean
  atomicity-envelope shape is pinned.
- `<path>='-'` stdin support — mirrors M31 `monday item upload`'s
  rejection rationale (no clean `--filename` companion shape pinned
  for `--set` syntax). Defers to v0.6.x once an extension shape is
  designed.
- `--set-raw <file-col>=<json>` — STAYS REJECTED per D3 closure.
  Files have no JSON wire shape `change_column_value` accepts; the
  escape-hatch contract is "user supplies the JSON Monday's
  `change_column_value` accepts" which doesn't compose with the
  multipart wire. v0.6.x may re-evaluate if Monday exposes an
  asset-id-reference wire shape for `change_column_value`.
- Cross-board `item move` value-overrides — carried over from v0.4
  + v0.5 release-prep slips. Monday's `ColumnMappingInput` carries
  no value slot at API `2026-01`; the richer `{id, value?}` form
  requires a non-atomic post-move `change_multiple_column_values`
  with cross-leg partial-failure envelope shapes. Out of v0.6
  scope; re-evaluate at v0.6.x or v0.7.
- Cross-board search resumable cursor — carried over from v0.4 +
  v0.5 release-prep; per-board cursor-lifetime under aggregation
  remains the load-bearing design issue. Not a v0.6 candidate by
  default.
- Multi-level subitem creation — carried over from v0.4 + v0.5
  release-prep; conditional on Monday's data model surfacing
  `subtasks` on `sub_items_board` at API `2026-01`+. Re-probe
  empirically before any v0.6 reopening; otherwise slips to v0.7.
- Profile-scoped argument defaults — filed at v0.6 kickoff
  candidate-selection session as a new feature candidate. Picks up
  at v0.6.x candidate-selection if user demand surfaces; carries
  its §13 carve-out Decision prerequisite forward (the "Saved
  queries / aliases" non-goal needs amending to distinguish
  aliases-as-stored-command-strings from defaults-as-stored-flag-
  values).
- OAuth app registration (`monday auth login`) — v0.5.0 still ships
  the M28 placeholder guard. Reopens only on clear user demand for
  browser-based login over `MONDAY_API_TOKEN`.

**Permanent non-goals (per cli-design §13 — reminded here so plan
readers don't propose them as v0.6 candidates):**

- Hosting webhooks (CLIs can't expose public HTTP — out of model).
- App framework / installable monday apps (different surface area).
- Real-time GraphQL subscriptions (Monday's endpoint doesn't
  support them).
- Telemetry, update-notifier, analytics — ever.
- Forms (Monday's public-submission feature) — same hosted-endpoint
  shape as webhooks.
- Saved queries / aliases — would silently change behavior across
  machines; shell aliases / shell functions are the established
  UNIX answer. **Note:** profile-scoped argument defaults (carried
  forward to v0.6.x — see "Out of scope" above) needs a §13
  carve-out Decision distinguishing aliases-as-stored-command-
  strings (still non-goal) from defaults-as-stored-flag-values
  (carve-out). That Decision lands at the milestone that picks the
  candidate.
- `monday undo` (replay-based reversal of recent mutations) —
  Monday's state model is authoritative and concurrent; honest
  substitutes are `--dry-run` (v0.1) and `item history` (v0.3-M24).

### M38 — files-shaped friendly `--set` writes

**Status:** pre-flight kickoff this session — contract diff lands
the dispatch stubs + cli-design §5.3 extension + new `src/api/file-
column-set.ts` module + parse-boundary mutex tests. Runtime body
ships at M38 IMPL once Codex pre-flight review converges.

**Wire surface.** Zero net change. M38 reuses Monday's existing
`add_file_to_column(item_id: ID!, column_id: String!, file: File!) →
Asset` mutation (v0.4-M31 probe-pinned). The novelty is the
**dispatch routing decision** at the CLI's translator boundary —
when `--set <col>=<path>` resolves to a `file`-typed column, the
action body branches OFF the standard JSON-translator path INTO
M31's multipart `addFileToColumn` fetcher.

**Two new CLI surfaces** (no new verbs, no new flags — extends
existing `--set` accepted-value grammar):

  - `monday item set <iid> <file-col>=<path> [--board <bid>] [--dry-run]`
    — single-column file write. Positional `<col>=<value>` grammar
    extended: when the resolved column has `type: 'file'`, the
    `<value>` is treated as a local file path (NOT a JSON-wire
    value). Path resolution + pre-check pattern mirrors M31's
    `item upload` (round-1 P2-2 R_OK leg included).
  - `monday item update <iid> --set <file-col>=<path> [--board <bid>] [--dry-run]`
    — single-`--set` file write. M38 requires EXACTLY ONE `--set`
    flag when a file-column is the target; mixing with value-`--set`
    / `--set-raw` / `--name` rejects at the column-resolution
    boundary with `usage_error.details.reason:
    'mixed_file_and_value_sets'`. Multi-file `--set` rejects with
    `usage_error.details.reason: 'multi_file_set_unsupported'`.

**Eight Decision closures pinned at pre-flight** (`§8 Decisions`
register below).

**Empirical probe — not required.** The wire shape is M31's
`add_file_to_column` mutation verbatim. The translator-boundary
dispatch design is contract diff work (pre-flight scope), not
probe work. The §5.3 translator architecture from M8/M12 + the
M31 multipart wire contract are both already pinned.

**No new ERROR_CODE** (D8 closure; registry stays at 29). All
M38-specific failures route through existing codes with `details.
reason` discrimination:

  - `usage_error.details.reason: 'mixed_file_and_value_sets'` —
    `--set <file-col>=<path>` mixed with any other `--set` /
    `--set-raw` / `--name` flag in same call. Rejects at column-
    resolution boundary (parse-time can't know — column type not

    `monday item update --board <bid> --where ... --set

  - `usage_error.details.reason: 'file_not_readable'` /
    `'file_empty'` / `'file_too_large'` — inherited from M31's
    `item upload` action body pattern verbatim.
  - `unsupported_column_type` — `--set-raw <file-col>=<json>`

  branch off the standard `--set` value-translator path?
  - **Closed at pre-flight contract diff (this session).** SIBLING
    BRANCH at the command action body, AFTER column resolution.
    The translator (`translateColumnValueAsync`) stays JSON-output-
    shaped for the 13 existing writable types; a new sibling
    module at `src/api/file-column-set.ts`

    Routing decision fires at the action body level: after column

    `executeFileColumnSet`; otherwise route to the standard

- **D2 — Mutex rules across `--set` / `--set-raw` / `--name`.**
  What mixing combinations does M38 accept?
  - **Closed at pre-flight contract diff.** EXACTLY ONE
    `--set <file-col>=<path>` per call, no other `--set` /
    `--set-raw` / `--name` flags allowed. Mutex enforcement at
    the column-resolution boundary (parse-time can't know — the
    column type only resolves after metadata loads). Rejection
    surfaces:
    - File `--set` + ANY value `--set` / `--set-raw` / `--name`
      → `usage_error.details.reason: 'mixed_file_and_value_sets'`.
    - 2+ file `--set` entries → `usage_error.details.reason:
      'multi_file_set_unsupported'`.

- **D3 — `--set-raw <file-col>=<json>`.** Does M38 lift the
  existing `--set-raw` rejection for file columns?
  - **Closed at pre-flight contract diff.** NO. Files have no

    `add_file_to_column` is the only file-write wire surface and
    it's multipart-only. The `--set-raw` escape-hatch contract
    ("user supplies the JSON `change_column_value` accepts")
    doesn't compose with multipart. M38 ONLY ships the friendly
    `--set <file-col>=<path>` form; the existing rejection at

- **D5 — Bulk `item update --where ... --set <file-col>=<path>`.**
  Allowed at M38?
  - **Closed at pre-flight contract diff.** REJECTED with

- **D7 — `<path>='-'` stdin support.** Allowed at M38?
