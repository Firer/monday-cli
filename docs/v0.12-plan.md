- **D1 — Precedence-resolver integration shape: DEFERRED to IMPL.**
  The runtime resolver that projects `[profiles.<active>.defaults]`
  table values onto CLI flags has 3 candidate integration shapes:
  - **(a) Per-command call-site.** Every command that accepts
    `--board`/`--workspace`/`--output`/`--concurrency` reads the
    resolved defaults via a runner-supplied `ctx.profileDefaults`
    slot and merges manually: `const board = opts.board ??
    ctx.profileDefaults.board`. Pro: explicit, easy to audit per
    command. Con: ~50+ files touched at IMPL; easy to forget a
    command on a future verb add.
  - **(b) Runner-layer merge BEFORE commander parse.** The runner
    mutates Commander option definitions to set `.default(value)`
    on each affected option after loading the config, BEFORE
    `parseAsync`. Commander's existing `.default()` machinery
    propagates the value, so commands see flags as if explicit
    defaults were set. Pro: one site of change; commands see no
    new shape. Con: requires walking the Commander tree;
    interaction with `--no-cache` / `--no-color` style options
    (which Commander treats specially) needs probing; changing
    option definitions at runtime may interact unexpectedly with
    `--help` rendering.
  - **(c) Runner-layer merge AFTER commander parse.** The runner
    intercepts `program.opts()` post-parse, merges the defaults
    into the opts bag, and threads the merged bag through `ctx`
    rather than via Commander's option store. Pro: no Commander
    tree mutation; one site of change. Con: commands that read
    `program.opts()` directly (not via `ctx`) bypass the merge —
    needs a cross-cutting audit to ensure all command bodies
    consume `ctx.opts` rather than `program.opts()`.
  Decision deferred to IMPL kickoff after the IMPL author probes
  the Commander interaction surface. The pre-flight contract pins
  the SHAPE (precedence chain semantics + key list + agent
  discipline) without binding the integration approach. **R-class
  watch-item**: R-v0.12-NEW-2 filed in §22 to surface the
  integration-shape Decision at IMPL kickoff with `AskUserQuestion`
  if the probe doesn't pick one option unambiguously.

- **D2 — `monday config get` output: RESOLVED-VALUE shape (not
  stored-value shape).** When the user runs `monday config get
  board`, the output reports the precedence-chain RESOLVED value
  (the same value a runtime command would see), with a `source:
  'env_var' | 'profile_default' | 'unset'` discriminator so the
  agent can audit where the value came from. Trade-offs:
  - **(a) Stored shape (rejected).** Output just shows what's in
    the TOML table. Pro: simple. Con: ignores env-var precedence
    layer; an agent running `monday config get board` while
    `MONDAY_BOARD=999` is set would see the stale TOML value, not
    the value the next `monday item list --board ...` invocation
    would actually use. Confusing.
  - **(b) Resolved-with-source (CHOSEN).** Output shows the
    resolved value + a `source` discriminator. Pro: matches the
    runtime semantics; agent debugging operator-side configuration
    sees ground truth. Con: ~2 extra schema fields; the `unset`
    case needs a sentinel shape (`value: null, source: 'unset'`
    via the discriminated-union pattern from `config show`).
  CLI-flag-as-source is NOT in scope for `monday config get` —
  the verb is a config-state read, not a runtime resolution; CLI
  flags would only be in scope when running the actual target
  command. The `--profile <name>` flag on `config get` scopes the
  read to a non-active profile (no other CLI flag interacts with
  the resolution chain at this surface).

- **D3 — `monday config set` rejection scope: existing
  `config_error` framings only (no new discriminator).** Per
  `.claude/rules/security.md` token-storage rule (tokens NEVER
  in config.toml) AND per the Codex pre-flight R1 P2-1 fold,
  `monday config set` is scope-limited to the
  `[profiles.<active>.defaults]` 4-key allowlist (`board`,
  `workspace`, `output`, `concurrency`) and rejects two classes:
  - **(a) Non-allowlist key.** `monday config set api_token
    <literal>` / `monday config set api_token_env <name>` /
    `monday config set api_version <ver>` (or any other non-
    allowlist key) all reject with `config_error
    details.reason: 'unknown_defaults_key'`. The existing
    `profileEntrySchema.api_token_env` parse boundary (which
    rejects token-looking values via the env-var-name regex
    `^[A-Z_][A-Z0-9_]*$/u`) is at the top-level
    `[profiles.<name>]` table and untouched by M55-E; editing
    that slot remains hand-TOML-only or indirect via `monday
    auth login` writing the credentials cache.
  - **(b) Wrong type on allowed key.** `monday config set
    board eyJhbGciOi...` / `monday config set workspace
    not-numeric` / `monday config set output yaml` reject with
    `config_error details.reason: 'wrong_defaults_type'`. The
    rejection surface is the per-key zod schema validation
    (`board` / `workspace` → `^\d+$`; `output` → `OUTPUT_FORMATS`
    enum; `concurrency` → `int().positive()`).
  Two existing `config_error` framings cover the rejection
  surface cleanly; no new `details.reason` discriminator added
  at M55-E. The R-v0.12-NEW-3 candidate filed at pre-flight
  (whether a dedicated `token_in_defaults_rejected` literal
  improves agent debuggability) was RESOLVED at Codex R1 fold

  `unknown_defaults_key` + `wrong_defaults_type`); the
  scope-limit fix from P2-1 makes the "token rejection"
  framing redundant since the verbs have no path to a token-

**D1 closure — option (c′) applicability-aware preAction
injection.** The pre-flight enumerated 3 candidate shapes (a/b/c)
+ deferred the binding decision. At IMPL kickoff the author ran
an in-tree Commander probe (8 cases) that eliminated (a) — the
`.requiredOption` mandatory enforcement fires BEFORE the action
body, so per-call-site merge in the action body can't apply for
required-flag commands; eliminated (b) — sync TOML + argv pre-
scan for `--profile` duplicates the existing async preAction
lifecycle; flagged (c) literal — blind `setOptionValueWithSource`
injection would break shipped contracts where the option is
mutex- or contextually-gated (`item create --parent` rejects
`--board`; `item update` requires `--board` only on bulk shape;
`update list` is XOR with `--board`; `item update --concurrency`
only on bulk + `--continue-on-error`). Codex IMPL-kickoff
consultation surfaced + recommended a 5th shape (c′): Codex's (c)
preAction lifecycle + a per-(commandPath, key) applicability
registry with optional preconditions gating each entry. User
binding via `AskUserQuestion` picked (c′) over the alternatives.
Three modules anchor the shape:

1. `src/config/profile-defaults.ts` — pure precedence-chain
   resolver `resolveProfileDefault(key, {env, profileDefaults})`
   returning `{value, source: 'env_var' | 'profile_default' |
   'unset'}`. Per-key env-var validation throws `config_error.
   wrong_defaults_type` on malformation. Two consumers: the
   application layer + the new `monday config get` verb.
2. `src/cli/profile-defaults.ts` — Commander application layer.
   `applyPerCommandProfileDefaults` walks the
   `APPLICABILITY_REGISTRY` per preAction, calls
   `setOptionValueWithSource(key, value, 'config')` for entries
   whose `commandPath` + precondition + option-absent gates pass.
   `applyProgramOutputDefault` handles the global `--output`
   injection (only when ALL of `--json` / `--table` / `--output`
   / `MONDAY_OUTPUT` absent — preserves the `select.ts` shorthand
   priority).
3. `APPLICABILITY_REGISTRY` (8 entries at v0.12-M55-E IMPL):
   - `item.list`, `item.find`, `item.upsert` → `board` (always-
     accepted).
   - `item.create` → `board` precondition `parent === undefined`.
   - `item.update`, `item.clear` → `board` precondition
