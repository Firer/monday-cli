- **D0 — §13 carve-out shape: distinguish aliases-as-stored-command-
  strings (still non-goal) from defaults-as-stored-flag-values
  (carve-out).** The pre-existing §13 "Saved queries / aliases"
  non-goal copy read "the CLI reads only from env/argv, with the §8
  cache as the sole derived state" — but `~/.monday-cli/config.toml`
  ALREADY exists (since v0.3-M21), so the prose was technically
  wrong even pre-E. The amendment:
  - **(a) Fix the env/argv inaccuracy.** New copy: aliases SILENTLY
    MUTATE COMMAND SHAPE — they change which subcommand runs, which
    positional args land where, which flags resolve.
  - **(b) Add the per-profile defaults carve-out.** Distinguishes
    flag-value resolution (carve-out — stays an argv-shape transform
    via the precedence chain) from command-shape mutation (still
    non-goal — aliases would change the parsed AST).
  - **(c) Pin agent-facing discipline.** Agents SHOULD set no
    defaults and pass every scoping arg in argv for reproducibility
    across machines; defaults are a human-ergonomics feature. The
    nudge lives in §7.2.1 + the 3 new verbs' help text + the §13
    amendment body. Folded at this pre-flight commit. Cross-refs
    §7.2.1 + §13 v0.12 entry + the v0.5/v0.6 carry-forward bullets'
    "picked up at v0.12-M55-E" updates.

- **D1 — Precedence-resolver integration shape: DEFERRED to IMPL.**
  The runtime resolver that projects `[profiles.<active>.defaults]`
  table values onto CLI flags has 3 candidate integration shapes:
  - **(a) Per-command call-site.** Every command that accepts
    `--board`/`--workspace`/`--output`/`--concurrency` reads the
    resolved defaults via a runner-supplied `ctx.profileDefaults`
    slot and merges manually: `const board = opts.board ??
    ctx.profileDefaults.board`. Pro: explicit, easy to audit per
    command. Con: ~50+ files touched at IMPL; easy to forget a
    command on a future verb add.
  - **(b) Runner-layer merge BEFORE commander parse.** The runner
    mutates Commander option definitions to set `.default(value)`
    on each affected option after loading the config, BEFORE
    `parseAsync`. Commander's existing `.default()` machinery
    propagates the value, so commands see flags as if explicit
    defaults were set. Pro: one site of change; commands see no
    new shape. Con: requires walking the Commander tree;
    interaction with `--no-cache` / `--no-color` style options
    (which Commander treats specially) needs probing; changing
    option definitions at runtime may interact unexpectedly with
    `--help` rendering.
  - **(c) Runner-layer merge AFTER commander parse.** The runner
    intercepts `program.opts()` post-parse, merges the defaults
    into the opts bag, and threads the merged bag through `ctx`
    rather than via Commander's option store. Pro: no Commander
    tree mutation; one site of change. Con: commands that read
    `program.opts()` directly (not via `ctx`) bypass the merge —
    needs a cross-cutting audit to ensure all command bodies
    consume `ctx.opts` rather than `program.opts()`.
  Decision deferred to IMPL kickoff after the IMPL author probes
  the Commander interaction surface. The pre-flight contract pins
  the SHAPE (precedence chain semantics + key list + agent
  discipline) without binding the integration approach. **R-class
  watch-item**: R-v0.12-NEW-2 filed in §22 to surface the
  integration-shape Decision at IMPL kickoff with `AskUserQuestion`
  if the probe doesn't pick one option unambiguously.

- **D2 — `monday config get` output: RESOLVED-VALUE shape (not
  stored-value shape).** When the user runs `monday config get
  board`, the output reports the precedence-chain RESOLVED value
  (the same value a runtime command would see), with a `source:
  'env_var' | 'profile_default' | 'unset'` discriminator so the
  agent can audit where the value came from. Trade-offs:
  - **(a) Stored shape (rejected).** Output just shows what's in
    the TOML table. Pro: simple. Con: ignores env-var precedence
    layer; an agent running `monday config get board` while
    `MONDAY_BOARD=999` is set would see the stale TOML value, not
    the value the next `monday item list --board ...` invocation
    would actually use. Confusing.
  - **(b) Resolved-with-source (CHOSEN).** Output shows the
    resolved value + a `source` discriminator. Pro: matches the
    runtime semantics; agent debugging operator-side configuration
    sees ground truth. Con: ~2 extra schema fields; the `unset`
    case needs a sentinel shape (`value: null, source: 'unset'`
    via the discriminated-union pattern from `config show`).
  CLI-flag-as-source is NOT in scope for `monday config get` —
  the verb is a config-state read, not a runtime resolution; CLI
  flags would only be in scope when running the actual target
  command. The `--profile <name>` flag on `config get` scopes the
  read to a non-active profile (no other CLI flag interacts with
  the resolution chain at this surface).

- **D3 — `monday config set` token-rejection scope: ALL token-
  shaped values reject at parse boundary.** Per `.claude/rules/
  security.md` token-storage rule (tokens NEVER in config.toml),
  `monday config set` rejects three classes of input:
  - **(a) Direct token-key rejection.** `monday config set
    api_token <literal>` rejects because `api_token` is not in
    the `[profiles.<active>.defaults]` key list (4 keys: `board`,
    `workspace`, `output`, `concurrency`). Standard "unknown key"
    `config_error`.
  - **(b) Token-shape rejection on allowed keys.** `monday config
    set board eyJhbGciOi...` rejects because the value doesn't
    match the BoardId shape `^\d+$`. Standard "wrong type"
    `config_error`.
  - **(c) The existing `profileEntrySchema.api_token_env` parse
    boundary** (which rejects token-looking values like
    `tok-fixture-xxxx` or JWT-looking values via the env-var-name
    regex `^[A-Z_][A-Z0-9_]*$/u`) covers the top-level
    `api_token_env` slot — unchanged at M55-E (the new `defaults`
    table is a SIBLING slot, not an extension of `api_token_env`).
  No new `details.reason` discriminator at the surface; the
  existing `config_error` framings (`unknown_key`, `wrong_type`,
  `token_in_config_rejected` for the existing top-level token-name
  shape) cover the rejection surface cleanly. R-class watch-item
  R-v0.12-NEW-3 filed in §22 to confirm at IMPL kickoff whether a
  dedicated `details.reason: 'token_in_defaults_rejected'`
  discriminator improves agent debuggability vs reusing existing
  framings.

- **D4 — Per-noun defaults: DEFERRED to v0.12.x candidate-selection.**
  Initial scope is 4 GLOBAL scoping defaults (`board`, `workspace`,
  `output`, `concurrency`) shared across noun namespaces. Per-noun
  extension — e.g., `[profiles.work.defaults.item]` with item-
  specific defaults — would let an agent configure different
  defaults per noun. Rejected at this pre-flight as scope creep:
  - The 4 initial keys cover the load-bearing scoping args (board,
    workspace, output, concurrency); per-noun extension is a
    separate design decision (do noun-defaults inherit from global
    defaults? does the precedence chain extend to 5 layers? how
    do they interact with `--profile <name>`?).
  - Per-noun extension would add ~10 noun namespaces × ~5–10 keys
    each = ~50–100 new schema slots and tests. The 4-key scope is
    a usable feature; the per-noun extension is a separate
    milestone.
  Deferred to v0.12.x candidate-selection. Filed as a §13 carry-
  forward at this pre-flight (in the v0.12 entry's "per-noun
  extension to other flags defers to v0.12.x" line).

- **D5 — ERROR_CODES delta: ZERO.** Registry stays at 29. The
  rejection surface routes through:
  - `config_error` (exit 3) for: token-in-config rejection
    (existing `profileEntrySchema` boundary), unknown-key reject
    (`.strict()` on `profileDefaultsBlockSchema`), wrong-type
    reject (zod type-mismatch on key values).
  - `usage_error` (exit 1) for: explicit empty-flag reject on a
    `--board ""` invocation (parse boundary; precedence chain
    doesn't surface a clear-the-default signal on the invocation
    side — `monday config unset board` is the right verb for
    that).
  - `not_found` is NOT in scope — `monday config unset <key>` on
    an absent key is idempotent no-op `ok: true` per the §3.1
    "Idempotency" rule + the `monday auth logout` precedent.
  `details.reason` discriminators added at this milestone (all
  RESERVED post-IMPL per R-NEW-82's reserved-literal discipline):
  - `token_in_defaults_rejected` (candidate per D3 — final shape
    decided at IMPL).
  - `unknown_defaults_key` for `.strict()` reject on
    `profileDefaultsBlockSchema` parse.
  - `wrong_defaults_type` for type-mismatch on a key value (e.g.,
    `board = 123` integer where string-numeric expected).
